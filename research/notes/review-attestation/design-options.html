Review Attestation Design Options

Design step · fifth draft · 27 November 2026

A thread’s sandbox checks and reviews. GitHub verifies its receipt, and the runner looks again.

A thread edits and commits in its sandbox. One command there starts a compiled, pinned program on the commit. It takes a clean checkout, works out from the delta which checks the change can affect, runs those and main’s reviewers side by side, prints the findings and signs what ran into a receipt. When the thread opens a pull request, GitHub runs no check and no reviewer for what the receipt covers. It verifies the receipt with code alone: the pinned program, the exact tree, and that nothing main requires is missing. A receipt made this way is the author’s own statement, so the runner stays the second party. It goes first on the paths you own, and after every merge main’s CI runs every gate again and a workflow reviews the merged change again. This draft answers your question of 27 November, whether two sandboxes are needed, and builds on the status quo research. Nothing here is implemented.

Judgement

Recommendation. Build it as drawn, in the five steps of section 9. Start with the program in a thread’s own sandbox, signing a receipt for every push while today’s CI and review still decide. Beside it, have a workflow on main review each merged change again. Neither changes what a merge depends on, and after about twenty pull requests two rates exist that nobody has today: how often a receipt and the runner agree, check by check, and how often two reviews of one change agree. Then let a thread’s own receipt stand in for the review and for the Linux gates of a pull request on ordinary paths.

A receipt made in one sandbox is the author’s own statement. The author is root where it is signed, so forging one takes nothing but the will to. What makes it safe to accept is what stands around it. The verify job recomputes everything that can be recomputed, so no stale, partial or wrong-tree result passes. Main’s CI runs every gate again after each merge, so a false line for a gate is found within one run, with the signed receipt as proof. A review is the part nobody can recompute, so the runner reviews merged changes again, all of them at first, and opens an issue for each blocking finding a receipt did not have. And for the paths you own the runner stays in front of the merge, where a wrong merge does damage that a revert does not undo. Whether that footing is enough is the one decision this page needs from you. It is in section 7, with what a second sandbox would add.

ParleyInn gets its first user this way, and its model has the class for it: a check the editing run started is an own check, one above a claim. For a second party it has a CI key and a CI attestation. It has no part that signs either statement. Section 8 proposes the parts, names the requirements that would change, and recommends an order: the prototype now, then the product on ParleyInn’s own record.

Today a thread that passes its local review still meets a fresh roll of the same reviewers in Actions, and a miss there costs another ten to fourteen minutes. In this design the fresh roll still happens, after the merge, and what it finds becomes an issue and not a wait.

Inside its own VM a session’s signature is that session’s signed claim.

A session can read any key in its VM, attach a debugger to the signer, or put another program in its place. A pinned hash in the receipt tells the verify job which program was meant to sign. It cannot tell it that this program did. That holds for a check service as it does for a thread: its agent is root in its VM too.

ParleyInn’s own threat model says the same of any node whose agent runs as its principal’s OS user. The agent “replaces ParleyInn’s executables” (R2) or “signs events with the node’s device key or a seat key” (R3), and the risks “remain while an agent runs unsandboxed as its principal’s own OS user”. A web session puts the agent and the key inside one VM, which is that case. ParleyInn would not even call this VM a sandbox around the run: a sandbox state is “recorded from outside the sandbox, where the agent cannot write”, and nothing outside this VM records one, so the run counts as unsandboxed and leaves every residual risk open. The open question OQ-40 asks for “a signing key no process of the OS user but the measuring component can read, such as a platform key store entry limited to its signed executable or a hardware key”. A web sandbox has no such key.

A second sandbox changes who would have to lie.

With one sandbox the author signs its own work. With two, the receipt is signed by a session that did not write the change, on a clean checkout of the pushed commit, with a key whose public half you enrolled on main. The verify job can then tell the two sessions apart, which git and GitHub cannot.

For a false receipt a thread would now need one of four things.

  • It wins over the service’s agent with a message. A hosted service needs one message in every round to wake up, and its skill tells its agent to read nothing in it but a commit id. A skill is guidance and not a wall.
  • It gets your approval for a move into the service’s environment, if the key is saved there.
  • Code in its tree breaks out of a run that has no privileges. That takes a flaw in the kernel.
  • It starts a session of its own in the service’s environment. I did not try whether a thread can. Step 2 has to rule it out before any receipt counts.

The third draft called a second session “tidier” and “not stronger evidence”, because both sessions act under your one account and one git identity. That was too quick: an enrolled key that only the second sandbox holds does tell them apart. The fourth draft then leaned on it too hard. The first of the four things is a message to a model, and a hosted service has to read one in every round, to wake up. Section 7 weighs what the second sandbox buys against what it costs.

It is still short of proof, and the hard part is the key.

The service’s agent is a model and is root in its VM. So what the service’s key signs is the service’s word, one party removed from the author. It is not a measurement taken from outside.

The research put the question for this design in one sentence: where does the validator’s key live, relative to the code it runs? A service that checks a thread’s commit runs code the thread wrote: build scripts, procedural macros and tests. SLSA’s rule for a hardened build is that the signing secret “MUST NOT be accessible to the environment running the user-defined build steps”.

So the program runs the tree’s code as an unprivileged user in namespaces of its own, with no network and no way to the key file, as the first table’s row on a process without privileges tried. That is separation by user and namespace inside one kernel. It is weaker than two machines, and it is what one VM allows. The program does the same in a thread’s own sandbox, where it keeps a build script or a test from touching the receipt or the network behind the author’s back. Judgement what it is worth

A receipt still changes what can go wrong, whoever signs it.

Without a receipt the claim is a sentence a model writes: all gates pass. A model can write that from a stale run, from a partial run, by mistake or under pressure. With the pinned program the model writes nothing. A program runs main’s commands on the committed tree and signs the exit codes.

A receipt can then be wrong in only two ways. Either somebody forged it on purpose, or the check itself is unsound. A stale receipt, a partial one, one for another tree or one made with other tools fails at the verify job, which recomputes all of that.

ParleyInn’s ranking of evidence has a class for each signer. A check the editing run started is an own check, one above a claim. A check’s exit status for the exact commit, signed with a CI key that the room’s owner enrolled, is a CI attestation. Once the CI bridge has brought it into the room, the result it backs is CI attested, the top class. Section 8 says how the receipt fits them.

Judgement the four uses

Deterministic means the same inputs give the same signed bytes.

The signed body holds no clock and no randomness: fields in one fixed order, digests in one spelling, durations kept outside it. That is the rule the invariant I10 sets for everything derived, and CI already fails a build whose derived artifacts read a clock or randomness.

Ed25519 is deterministic by construction: one key and one message give one signature. So two honest runs on one tree, with one key and the same receipt before them, produce the same receipt, byte for byte.

The build is pinned, not reproduced. ENG-19 asked two builders to agree on the bytes and was withdrawn on 10 October. A pin needs less: one build made by a workflow on main, with provenance that names the commit and the workflow, as ENG-20 requires of release artifacts. Whoever adds a hash to the pin checks that provenance once.

A check’s output is not compared byte for byte, because test output carries timings and thread order. The receipt keeps a digest of the output as evidence. A second run compares the exit status and the figures the check defines, such as a coverage percentage.

5The verify job on GitHub

The workflow part. One job that main defines, with no agent and no Claude token, decides from the receipt, the repository, main’s pins and main’s policy file, which says what each kind of signer may answer. It is the same job whoever signed the receipt.

Every gate main requires is answered once, by one of three sources.

For each gate in main’s list the verify job computes the input digest on the tree that would land. Then it looks for an answer in this order.

  • The receipt. A line for that gate with the same input digest and exit status 0, in a receipt that passed the checklist below. A head can have two receipts: the fast checks and the review first, global checks later.
  • Main’s own last CI run. The gate’s inputs are the ones main already passed, so this change cannot have altered its result. This source needs the declared inputs of step 4.
  • The runner, now. Today’s CI job for that gate.

A gate that the first two leave open is a gap, and a gap is never a failure. It is a job. A pull request with no receipt at all is one large gap: it gets today’s CI and today’s review. So nothing changes for a branch a person pushed from a laptop.

The jobs keep their shape. Every CI job already runs its gate through scripts/ci-gate.sh, so that script can ask the pinned verifier first and end at once when the gate has an answer, with a line in the job summary that names the receipt. A job that is its own definition gets the same first step. Estimate A job that ends this way costs its start. The smallest jobs of the measured run did 9 to 14 seconds of work.

Judgement the three sources

The verify job’s checklist

The job posts a pass only when every line holds. A line that fails for one gate or one reviewer sends that gate or reviewer to the runner. Each refusal is counted in the job summary with its reason.

  1. The receipt reads. It parses under a strict schema and fits its size caps. No model ever reads it.

  2. The signatures verify, and main’s policy allows the signer. The receipt’s own signature verifies under the key the receipt names, and the platform’s signature over the commit that carries it verifies under the key main lists for web sessions. A key that main’s policy file does not name is an author’s own. Such a receipt may answer the gates a sandbox can run and the review, on ordinary paths. A key the file names may answer what the file says.

  3. The build it names is one main pins. The sha256 in the signed bytes equals a checksum in main’s mise.lock.

  4. Its pins are main’s. The gate list, the toolchain and the lock files it names are those of the main the job sees. A line made under other pins is a gap.

  5. Its subject is this change. The receipt names the pull request’s head commit, the tree it names is the tree the job computes, and the commit that carries it holds nothing but receipts.

  6. Every input digest matches. The job recomputes each one from main’s gate list and the tree, line by line.

  7. Nothing is missing. Every gate main requires for this change has one of the three answers.

  8. No failure is taken on weaker evidence. A line with another exit status than 0 is a gap, and a gap’s job has to pass on the runner.

  9. The path class is respected. A policy file on main says for which paths the runner runs everything before the merge. For those, every gate and every reviewer is a gap, and the receipt is compared with what the runner finds.

  10. The review holds. The lines of section 6: the answer keys match, the dispatch is covered, each report passes the report check again, main’s decision code approves, the findings that turn on your consent are recomputed now, and a changed reviewer was evaluated on the runner under ENG-32.

  11. It is the first answer for these inputs. A second receipt with another answer for an input digest the job has already seen is refused, so no signer can run a check until it passes once and send only that. The program signs every commit it checks, pass or fail, and each receipt names the one before it. A receipt that was left unpushed shows as a gap in the chain, and a chain with a gap is refused. An author could still write a whole new chain, and that is forging, which section 7 weighs.

  12. Main is green. The last finished CI run on main passed. If not, no receipt counts until it does.

The merge ruleset requires two checks on the head commit: CI, from any source, and review-gate from the review app. Neither changes.

CI is the last job of the pull request’s own copy of ci.yml, so it runs the pull request’s workflow and scripts. That is so today, and it is why .github/ and scripts/ are paths you own. review-gate is posted by a workflow that main defines and that reads the pull request as data. The verify job belongs there. It takes the gate list and the pins from main and posts review-gate only when the checklist holds, with every gap’s job passed.

Judgement the stop

Six details of today’s workflows need care.

Before a pull request exists the order is free. The thread commits, the program answers in the sandbox, and nothing has to be pushed. When the head has a passing receipt, the thread pushes the head and the side branch with the receipts, and then opens the pull request. The verify job starts when CI is requested and finds the receipt there. It looks again when CI completes. GitHub does not send the requested event when a workflow is re-run, so the job keeps listening for completed, as the review does today.

Once the pull request is open, every push to its branch starts CI at once. In a later round the thread therefore pushes the receipt’s branch before the head, so that the receipt is there when the verify job looks. With a check service the order would be the other way round: the push comes first, the receipt later, and such a round costs today’s CI.

The review workflow’s concurrency group lets a newer CI event cancel a running review. The verify job needs a group of its own, or CI’s completion would cancel the job that waits for it.

Where main’s workflow runs a pull request’s code, as it does when the runner runs a gate again for comparison, that job holds no secret and no write permission.

The policy file is read from main and never from the pull request, like the gate list and the pins. A pull request that changes it is a change to a path you own.

The second look is a workflow on main that a push to main starts. It holds a Claude token of its own, reads the merged change as data and can write nothing but an issue.

The one choice that changes what a pass means. On the evening of 27 November you asked whether two sandboxes are really needed. This section lists what the second sandbox gains, point by point, then what can hold each gain when there is only one sandbox, and then the four options with the changed recommendation.

Judgement

Your question: “I am wondering if we really need two sandboxes.” No, not for the speed and not for the gates. Of the ten gains the fourth draft credited to the check service, five never depended on the second sandbox: they come from the pinned program and from the verify job, which recomputes them wherever the program ran. Three depend on it in part. Two depend on it fully, and one of those matters for the quality bar: the reviewers’ reports are written where the author cannot write.

The second sandbox holds that gain only softly, because any thread can write to the service’s agent, and a hosted service sleeps between rounds. Inside one hosted sandbox nothing can hold it at all, because the author is root there and no layer lies beneath it. What one sandbox can have is a second party outside it. The runner is that party: in front of the merge on the paths you own, and behind the merge for every change, where nobody waits for it. That is detection after the merge and not prevention. Prevention on every path needs a witness with a real wall. Three exist, and the table “Who can write the review’s record” has them.

So the recommendation changes to one sandbox for each thread, checked from outside. It is option 1 below.

That wall is soft, and a hosted service sleeps.

A thread cannot read the service’s files. It can still get a false receipt signed in four ways, which section 2 lists: a message that wins over the service’s agent, your approval of a move into the service’s environment, a break-out from a run without privileges, and a session it starts in the service’s environment, which nobody has tried. New since the fourth draft: a hosted session’s VM does not keep running. The sandbox is not a black box

Your next remark: “This assumes the sandbox is a blackbox”. It did. The table above treats the receipt as the only thing that leaves the sandbox. More leaves it, and that changes how B2 to B4 can be found.

A session’s agent can act only through tool calls, and a record of them exists outside the sandbox.

  • Every action of the agent is model output. The agent changes nothing in its VM except by emitting a tool call, and the model that emits it runs on Anthropic’s side. So the first command of any tampering was produced outside the VM, whatever the VM reports afterwards.
  • The transcript can be read by another session. A session of this project can list another session’s transcript events: user messages, assistant responses, tool calls and hook events, with shell commands among them.
  • All traffic leaves through the platform. Model calls, git pushes and every other connection go through the platform’s proxies. Whether you can read those logs I do not know.

So a forgery does not only have to produce a receipt that verifies. It also has to be absent from a record the forger does not keep.

An auditor that reads the run’s record is the one check that reaches a single forged review.

The auditor does not look for tampering, which would be a judgement about arbitrary shell commands. It checks the opposite, which code can do: between the commit and its receipt the session ran the one loop command, and from the start of the session no command wrote to the program’s directories, the toolchain, the key or the answer store. A session that fails that check has a receipt that does not count, and its review goes to the runner.

Four limits.

  • The record is reported by the harness, and the harness runs in the VM. A session that had already taken over its harness could report what it liked. The command that takes it over comes first, though, and is reported while the harness is still honest. I did not establish whether the events another session reads are Anthropic’s own copy of the model’s output or the harness’s upload. Anthropic holds the first in any case.
  • A command can hide what it does. A script the agent wrote, or one that the change itself carries, does things no tool call names. So the check is strict about where commands may write, and what it cannot follow it refuses.
  • The change’s own code runs without tool calls. C1 stays a matter for the unprivileged run.
  • The reader is a session. I found no way for a workflow on GitHub to read a transcript. A hosted session sleeps when idle, and its agent fetches the events before code reads them, so the auditor is a second party of the same soft kind as a check service. It needs no key and runs no check, which makes it much smaller.

This is also what ParleyInn is for: an append-only record of every run, kept where the agent cannot rewrite it, from which an own check is derived. Way A of section 8 is that record with a signature, so the white-box view gives way A more weight than a receipt alone has.

b) The same gains with one joint sandbox

A wall inside a sandbox needs a layer beneath the agent, and a hosted sandbox offers none.

To hold row 7 inside one sandbox, something there would have to run the reviewers and keep a key where the session’s agent cannot reach. A wall like that is always held by a layer beneath the one it confines: a kernel beneath an unprivileged user, a hypervisor beneath a VM, a chip beneath a kernel.

In a hosted sandbox the agent is the top of its VM. It is root with 40 of 41 capabilities, the kernel has no security module, and there is no hardware key. The only layer beneath is the platform’s, and what the platform does for a session there is sign its commits. The program can fence in the tree’s code, because the program is above that code. Nothing in the VM is above the agent.

The four options

The options differ in who signs the receipt and in what else has happened by the time a change merges. Options 1 and 2 come with one rule for the paths you own, which follows them.

1

One sandbox: the thread’s own receipt, with the runner behind it

The author’s signed claim, looked over from outsideRecommended

The thread runs the pinned program in its own sandbox and signs. On ordinary paths the verified receipt is enough to merge. The runner goes first on the paths you own, and after every merge it runs every gate again and reviews the change again.

How it works

  1. The thread commits and runs one command. The program checks the commit out cleanly, runs what the delta can affect and main’s reviewers side by side, and signs a receipt with a key of the session.
  2. The thread reads the failures and findings and goes round again. Once the receipt for its head passes, it pushes the head, pushes the receipt on a side branch, and opens the pull request.
  3. The verify job works through its checklist. A policy file on main says that an author’s receipt may answer the gates a sandbox can run and the review, on ordinary paths. What the receipt does not answer, and everything on a path you own, goes to the runner.
  4. After the merge main’s CI runs every gate on the merged tree. A gate that contradicts a receipt opens an issue, and receipts stop counting until main is green.
  5. After the merge a workflow on main also runs main’s reviewers on the merged change, on every change at first. A blocking finding the receipt did not have opens an issue.
Variant: the runner reviews before the merge

The receipt answers the gates, and the runner still writes the review, started at once and no longer queued behind CI. ENG-21 then stands as it reads today. Estimate While CI’s slow jobs are still in front, at step 3, this costs no time, because they take as long. At step 4 it is the difference between about half a minute and four to seven.

Variant: hosted reviewer sessions write the review’s record

Each reviewer runs as a hosted session at Anthropic, started from the thread’s sandbox, with the repository mounted at the head commit. The verify job reads each session’s events with a key of its own: the agent’s version, the commit, the one prompt and the report. The author never holds the record. It does nothing for the gates.

Variant: a keeper on a machine of yours

The joint sandbox with a wall, as drawn above. The thread runs as an unprivileged user in a self-hosted environment, and a keeper under another user runs the program and signs with a key you enrolled once.

What it gives

  • No second session, no key to enrol, no hop and no queue. Checks and reviewers run beside the editor, on its disk.
  • Every honest mistake is caught before the merge: a stale receipt, a partial one, one for another tree, other tools than main’s.
  • A false line for a gate is caught within one CI run of main, with the signed receipt as proof.
  • Every merged review is looked at again by reviewers the author cannot reach, and no pull request waits for that.
  • The second look gives the rate at which a sandbox review and a runner review agree. That rate says whether a witness is ever needed.

What it costs

  • The author signs for itself. Forging a receipt takes nothing but reading its own key.
  • A forged or chosen review is found only after the merge, and by another roll of the reviewers. A finding shows what the change lacked. It cannot prove that a report was forged.
  • Until main’s run and the second look have ended, the author’s statement is all that stood behind a merge on an ordinary path. That needs your ruling on ENG-21, which is decision 2.
  • At first the runner reviews every merged change, which is the spend of today’s review moved behind the merge.
  • A thread needs a standing permission to push a side branch for each pull request.

Judgement This is the option I would build. Everything an honest thread can get wrong is caught before the merge by code. Everything a dishonest one can do is looked at again by a party it cannot reach, at the latest one run of main later. It is the shortest loop, it needs nothing from the platform that I have not seen work, and the second look measures whether more is needed. If more is needed, a witness for the review is one line in main’s policy file, and neither the receipt nor the verify job changes.

Two sandboxes: a check service signs

A second party’s signed claim, under a key you enrolled

The thread edits. A check service in a sandbox of its own runs the program on each pushed commit and signs with a key the thread cannot read. This was the fourth draft’s recommendation.

How it works

  1. You start one session as the check service, in an environment of its own, and enrol the public half of its key in main’s policy file.
  2. A thread commits, pushes and wakes the service with a message that holds the commit id and nothing else. The service fetches the commit, runs what the delta can affect and main’s reviewers, and signs a receipt for that commit onto its own branch.
  3. The thread reads the failures and findings and goes round again. Once the receipt for its head passes, it opens the pull request.
  4. The verify job checks the signature against the enrolled key and works through its checklist.
  5. Main’s CI runs every gate again after the merge, a share of merged reviews is looked at again, and a contradiction stops the receipts.
Variant: one service beside each thread

A service for each thread has no queue and no neighbour. It costs a key to enrol and a cold build for each one.

Variant: a machine of your own

A service on a machine of yours does not sleep and keeps its disk and its key. Put on the machine the threads run on, it is the keeper of option 1’s third variant.

What it gives

  • The author no longer signs its own work, and no longer holds the reviewers’ reports before they are signed.
  • One build that stays and one store of answers for every thread, and the editor’s own cores stay free while a round runs.
  • It is the shape ParleyInn’s model already names: a CI key and a CI attestation.

What it costs

  • It is still a claim. The service’s agent is root in its VM, and any session of your account can write to it.
  • A hosted service sleeps after a few idle minutes and wakes without its program. Every round then starts with a message from the thread and a turn of the service’s agent.
  • A hop and a queue. Each round is a push, a wake-up and a fetch, and one service serves all threads.
  • A key to enrol, and to enrol again whenever the service’s VM is reclaimed.
  • Whether a thread can start a session in the service’s environment was not tried.

Judgement The second sandbox buys the review’s record on ordinary paths, softly, and pays for it with a hop, a wake-up and a session to keep. I would not start here. It stays a witness that can be added later, if the second look shows that receipts approve more often than the runner does.

3

The runner decides, and no receipt counts

The runner’s own run, before the pull request

The thread drives the loop from its sandbox and calls main’s workflows for each round. Gates and reviewers run on the runner, and when the pull request opens every answer is already there.

How it works

  1. The thread pushes its branch and starts main’s workflows for that commit. Threads here have a tool that starts a workflow run.
  2. The runner runs the gates and the review as today and keeps each answer by input digest, in a store only main’s workflow fills.
  3. At the pull request the verify job finds an answer for every gate and reviewer and posts at once.

What it gives

  • Today’s assurance, unchanged. Nothing rests on a session’s signature.
  • No second roll, since the round the thread waited for is the one that counts.

What it costs

  • The work is not in a sandbox, which is what you asked for.
  • Estimate A round takes about as long as CI and the review take today, five to fourteen minutes on the measured pushes. A faster runner such as Depot’s would shorten the CI part.
  • Every round is a push and a set of runner jobs.

Judgement This is the fallback of options 1 and 2 with a handle on it. It is the answer if no session’s signature should ever decide a merge.

4

A signer no session can reach

Not offered by the hosted platform today

Something outside every VM sees what a session ran and signs that. The receipt would then be proof and not a claim, with no runner and no second sandbox.

What exists

  • The platform signs every commit of a session with a key outside the VM. It signs where the commit came from. It does not see or sign what ran, and one key signs for every session.
  • The documentation names no signed record of a session, and no interface through which a workflow could read a session’s transcript.
  • For the review alone there is a way, which is the second variant of option 1: each reviewer as a hosted session whose events the verify job reads from Anthropic.

What it would take

  • A request to Anthropic for a signature over what a session executed: the command, its exit status and the tree. That is the same statement ParleyInn’s open question OQ-40 asks a measuring component to sign.
  • Or a machine of your own, where the layer beneath the agent is yours. That is the third variant of option 1.

Judgement Worth asking for, because it would make a receipt as strong as a runner’s result. No plan can rest on it.

The rule for the paths you own, under options 1 and 2.

For a pull request that touches a path you own, the whole of CI and the review runs on the runner before the merge, as today, and the receipt is compared with what the runner finds. A policy file on main lists the paths. It starts as CODEOWNERS: the agent instructions, the reviewer definitions, the review tools, the workflows and scripts, the manifests, the tool pins, the bans and acceptances. The policy file itself joins it.

Such a pull request waits for your own review in any case, and the runner works in that time. So the rule adds no wait where you are the wait already. It also gives a standing comparison of receipts with the runner, on exactly the pull requests you look at yourself.

Its price is that many changes are in the class while the review itself is being built. From 13 to 26 November, 28 of the 51 changes on main touched a path you own. A narrower list of the workflows, scripts, pins, bans and the verify job’s code would have caught 9, and 17 with the reviewer definitions added.

Judgement Keep the rule whoever signs. A receipt should never be what lets a change to the checking through, because a wrong merge there can switch the checking off, and a revert does not undo that. Start the list as CODEOWNERS and narrow it once the comparison shows that receipts and runner agree.

Variant: no rule

A verified receipt is enough on every path. It is the shortest wait for every change, and a forged receipt can then land a change to the workflows, the pins or the verify job’s own code.

Variant: a drawn share on ordinary paths as well

Main’s workflow draws, from a keyed hash of the head, the gate and a secret only it holds, which answered gates the runner runs again before the merge. No session can know a draw before it pushes. A run that disagrees with the receipt fails the check and opens the issue of section 5. It buys prevention on the drawn share and costs that gate’s run time on the wait.

What holds in every option

  • Other tools or reviewers than main’s. A different toolchain, gate list, definition, model or CLI yields a digest the verify job never asks for.
  • A stale result. Input digests and answer keys are content hashes, so an answer for other inputs has another digest.
  • A result from another pull request. Harmless when true, since an unchanged input digest is the same question.
  • A change that edits its own checks. Main’s workflow, main’s gate list and main’s definitions decide, those paths need your consent, and a changed reviewer is evaluated on the runner.
  • Injection through the receipt. Strict schema, size caps, escaped strings, and no model reads it.
  • A silent fallback. Every refusal and every gap is counted in the job summary with its reason.
  • A pull request with no receipt. It gets today’s CI and today’s review. Pull requests from forks are not reviewed today, and no option changes that.

9Steps and decisions

Five steps. Each one is useful if the next never happens, and the first two change nothing a merge depends on.

  1. Sign a receipt for every push, beside today’s CI and review

    Nothing counts yet · no new trust

    The prototype of section 8: one pinned executable that runs main’s gates on the committed tree, signs the receipt and verifies it. It runs in the thread’s own sandbox with a key of that session, as the program of section 4, and the thread’s git commits the receipt to a side branch. review-local.sh is changed to run main’s tools and definitions and writes the review’s part. On GitHub the verify job works through its checklist, holds every line against what the runner found for the same input digest, and writes the differences into the job summary. It decides nothing.

    Done after about twenty pull requests, when every difference between a receipt and the runner has a cause that is written down. The measurements for this page found three such differences already. They are in section 4. The step adds a job to a workflow and a pin, which are paths you own, so its pull request asks for your review once.

  2. Start the second look on main, still beside CI

    Nothing counts yet · no new trust

    A workflow on main reviews every merged change again with main’s reviewers on the runner. In this step every pull request still has today’s review before the merge, so each merged change has three reviews to compare: the runner’s before the merge, the runner’s after it, and the receipt’s.

    This step measures what the page could only estimate, and what decision 1 turns on. How often does the runner disagree with itself on one change? How often does an author’s receipt disagree with the runner, and is that more? What does a round cost on four cores that the editor shares, and what does the second look spend?

    Done when the two rates exist for about twenty pull requests and every disagreement has a written cause. If an author’s receipts disagree with the runner clearly more often than the runner does with itself, the review goes back to the runner before the merge, which is variant (a) of option 1, or a second party signs it. Needs your consent for the workflow.

  3. Let the thread’s own receipt count on ordinary paths

    The choice of section 7 · the author’s signed claim, where you allow it, with the runner behind it

    The verify job posts review-gate. Under the recommended option it accepts an author’s receipt for the review and for the checks a sandbox ran, on every path you do not own, as main’s policy file says. A check that has not yet declared what it reads counts as reading the whole tree, so the program runs it whole on every commit, which is slower and never wrong. After each merge main’s CI runs every gate again, and a contradiction stops the receipts. The second look of step 2 goes on for every merged change. Estimate The check then arrives when CI ends: about 5 min 36 s after the first measured push, where it took 9 min 51 s. The second measured push added a reviewer, which is a path you own, so it would have gone to the runner as today.

    Needs your consent, because it changes the workflows, the review’s tools and what a pass means. It also needs your ruling on ENG-21, which is decision 2, a change to ENG-28 for a carried review, and a decision record that says all of it.

  4. Every check declares what it reads

    The same trust · less work on both sides

    Main’s gate list gains what each check reads, its class and its time budget, check by check. The program then runs a check only when one of its inputs changed, and on GitHub a gate whose inputs main already passed needs no run. A change that no runner job has to see then waits for the verify job alone, which is where decision 4 comes in. The declarations change only main’s list and the program, so this work can begin as soon as step 1 runs.

    Done when each check’s declared inputs have been held against a trace of the files its run opened, and a drift case shows that a change to a declared input changes the digest.

  5. ParleyInn makes the statement from its own record

    The product’s form · the editing node’s own statement, or a CI key you enrol in a room

    Way A or way B of section 8, as decision 1 falls. Either starts as a use case under docs/use-cases. For way A the model gains the check receipt, and the core signs it for the editing node’s own checks. For way B the model says who may hold a CI key, who may be enrolled, and which part makes a CI attestation. Then come the requirements with their scenarios and, for way B, a decision record that a named security reviewer approved, in a plan that pulls parts of M7, M8 and M9 forward. The verify job then calls parinn, and the prototype’s signing retires. Both can run side by side first, the way steps 1 and 2 run beside CI.

    This is the step in which ParleyInn itself is used on its own repository. Steps 1 to 4 use a prototype in this repo’s tooling and do not wait for it.

What a pass means once receipts count.

On a pull request whose receipt covers everything, a pass then says: main’s checks and main’s reviewers, on exactly this tree, with nothing missing, by main’s rule, on the author’s own signed claim that the pinned build ran them.

The first decision record behind the review, since superseded, said that “the rest of the pipeline must hold even when the agent is fooled or wrong”, and its successors keep the gate it set up. For the checks the pipeline still holds, one CI run of main later. For the review it rests on the author until the second look has run: the author’s program ran main’s reviewers and signed their reports, and nothing can run them again with the same answer. A forged review on an ordinary path would therefore land, and be found afterwards. That is the reason step 3 needs a ruling and a decision record of its own, and the reason the recommended option keeps the runner in front of the merge for the paths that hold the checking.

One thing shrinks what rests on anyone’s word, in every option. Each finding that can become a deterministic check should become one. Anyone can run such a check again, and main does after every merge. The repo already moves that way with its drift cases and the bundle’s deterministic findings.

Decisions that are yours

Only the first is needed to go on, and it is the decision card in the thread. Each of the others can wait for the step that raises it, and each has my recommendation.

  1. Is one sandbox per thread enough for a receipt to count? Decided on 28 November: option 1.

    The four options of section 7. I recommend option 1 with its rule: the thread’s own sandbox checks, reviews and signs, its verified receipt is enough on ordinary paths, the runner goes first on the paths you own, and after the merge main’s CI runs every gate again and the runner reviews the change again. This is the one decision the design cannot move without. Steps 1 and 2 are the same under every option.

  2. May an author’s own receipt carry the review that ENG-21 asks for?

    ENG-21 says “every pull request MUST be approved by a reviewer other than its author”. With one sandbox the reviewers are other agents in fresh contexts with main’s definitions, and the verify job, which approves, authors nothing. But the author’s session ran them and holds their reports before they are signed. I would rule the requirement met on ordinary paths while the runner reviews every merged change again, and write that into ENG-28 and a decision record. If you rule the other way, variant (a) of option 1 keeps the runner’s review before the merge and lets the receipt answer the gates alone.

  3. How does ParleyInn come to provide it, who may hold a CI key, and who is the security reviewer?

    I recommend the prototype now. With option 1 the product’s form is way A of section 8, and way B only if you want a second party before the merge. The domain-model agent puts two questions to you that bear on way B and that the model does not answer. May an editing node of the room’s owner sign CI attestations, when a witness check ranks below them and that node can run none? And which part holds the signing half of a CI key, out of every agent’s reach? ENG-29 asks for a named human security reviewer on the decision record before the product’s form is built past a prototype.

  4. Which global checks must finish before a merge when a change gives them nothing new to see?

    The drift suite is the large one: 24 shards on every pull request, ending 5 min 12 s after the measured push. I recommend the cases a delta touches in the sandbox before the merge and the whole suite on main after it, except on the paths you own. The others are the macOS build, the runs on Windows and Arm, the benchmark, miri and the end-to-end shards, each skipped when nothing it reads has changed. If all of them stay in front, step 4 gains about half a minute over step 3. If none does, a change that leaves the product’s code and your paths alone waits about half a minute in all.

  5. How long does the runner review every merged change again, and which share after that?

    With one sandbox the second look is the only second party a review on an ordinary path meets. I recommend every merged change until the two rates of step 2 exist and you have read them, and after that a share you set, with every change that touches the product’s code. It costs runner time and about one review’s spend for each change, after the merge and never a round before it.

  6. If you want a witness before the merge, which one, and where does its key live?

    Not needed for option 1. The witnesses of section 7 are a check service in a second hosted sandbox, hosted reviewer sessions, the runner, and a keeper on a machine of yours. The keeper has the only wall that is yours, and you would have to run the machine. The places for an enrolled key are in section 3.

  7. Is three the right number of rounds before a thread asks you?

    Three is what section 6 proposes and what Anthropic reports for its own review. With one sandbox the count is in the author’s keeping, so the cap is a rule of the skill. A second party would keep the count itself.

  8. Did I read three of your phrases as you meant them?

    “Deterministic”: the same inputs give the same signed bytes, from a build that main pins by checksum. It does not mean a build anyone can reproduce bit for bit, since ENG-19 was withdrawn on 10 October. “A sandbox running a shared chat”: a web session of this project, which shares the project’s chat, folder and repository with the threads. The fourth draft took the signing sandbox to be a second one, the one that validates. After your question this draft goes back to the thread’s own sandbox, and the second-sandbox reading is option 2. “Fast checks cannot be arbitrary”: a check may be called fast only while it keeps the five promises of section 4. If you meant that no thread may choose which checks run, the design holds that as well, since main’s list chooses.

  9. Should I draft a request to Anthropic for a signature over what a session ran?

    Option 4. It would turn a receipt from a claim into proof. I found no such interface in the documentation.
