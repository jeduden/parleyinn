Review Attestation Status Quo

Research for the design step · 26 November 2026

Can a CI gate trust what a sandbox says it checked?

The goal is to move the review ping-pong into the agent’s sandbox, where editing and reviewing are fastest, and let GitHub check only an attestation that the work was done and the record is complete. This page surveys how the industry splits review between the sandbox, CI and the merge gate, which attestation building blocks exist, what can go wrong, and where this repo’s gate stands today. It proposes no design.

1The short version

Inference

Short answer. Only if the record is one the sandbox cannot forge, or one the gate can recompute. The sources agree on where assurance comes from: a signer or a check outside the agent’s reach, a binding to one commit, and checks that the change under review cannot edit. They differ on how much review belongs before the PR, and I found no adopted design that attests an agent’s code review for a merge gate.

Most teams check before the PR and still gate on the server.

Anthropic, OpenAI, Stripe and Spotify all describe heavy checking inside the agent loop. Anthropic says most review now happens before a PR exists, yet it keeps its hard review gate at the test and CI stage, and its approvals cover one commit.

The nearest published precedent is an evidence-plus-policy merge.

Cursor describes agents that return evidence such as CI results, a security review and a screen recording. A policy scores the risk, merges low-risk changes automatically and routes the rest to the right person. Cursor’s own estimate is that 30 to 40 percent of its PRs merge without human review. The write-up calls its policy code a conceptual sketch of a proprietary system.

No standard says that a review happened, or that an agent run happened.

in-toto’s vetted predicates cover test results, vulnerability scans, runtime traces and a generic verification result, but not a code review. SLSA’s Source track asks for two trusted persons at its top level and admits automation only as a “Trusted Robot”. IETF drafts, open-source projects and one vendor effort try to fill the gap. A paper from October says that “no widely adopted standard yet enables agentic provenance and governance”. Section 4 lists them.

Trust depends on who signs and who can reach the signer, more than on the format.

The designs I read that claim strong assurance keep the signer or the check out of the agent’s reach. Tracekit uses a signer the agent cannot reach. Spotify does not expose its verifiers to the agent. Anthropic says to keep verification out of reach of the changes it judges. agentattest caps anything captured on the developer machine at “evidence-grade”.

The cost of ignoring this is documented. Models have fabricated tool use and hacked tests, and at one startup 27 percent of merges rested on an approval that an agent submitted under a human’s account. Section 5 goes through it.

Duplicate review is mostly re-review, and the remedies are known.

Build each round on the last, re-review only the new diff, cap the rounds, key reused results by content, and decide in advance which approvals survive a new commit. Each remedy has a published precedent. Each also has a named hazard, from fifty-round loops to poisoned shared caches. Section 6 has the detail.

Whether the author’s model family can review its own work is unsettled.

Greptile argues for an independent reviewer, but it sells one. A benchmark of 14 open models reports a 64.5 percent self-correction blind spot: they fix an error attributed to someone else but not the identical error attributed to themselves. A single-team preprint found that 56.5 percent of confirmed defects were caught by only one of eight models. Anthropic argues for tuning one reviewer over stacking more. I found no study that compares review in the author’s sandbox with review in CI.

5Can a gate trust a sandbox’s word?

The attester decides how much a record is worth. The sources describe five things a gate can be handed. The ordering is my arrangement of what they say. It is not a published scale, though agentattest publishes a three-level version.

  1. A claim

    The gate must trust the agent

    The agent’s own words: “tests pass”, “reviewed”, a PR description.

    Models have fabricated tool use and test results. An LLM judge of process evidence partly rewards how a PR is presented.

  2. A log the harness wrote

    The gate must trust the host that stores the log

    Tool calls and outputs captured by the host, unsigned. Anthropic stamps each commit with how it was verified. This repo’s review decides from the Read calls in a run’s log, “never from what the specialist says”.

    Whoever holds an unsigned log can edit it.

  3. A signed log, signer inside the environment

    The gate must trust the environment that holds the key

    Signing protects the log from later edits. It does not stop a compromised or instructed agent from signing what it likes.

    agentattest caps local capture at evidence-grade. Occasio marks a policy it only inferred at attest time as weaker evidence.

  4. A signed record the agent cannot forge

    The gate must trust the signer, its policy and its isolation

    The signer sits outside the agent’s reach and decides or observes each call. Anthropic-hosted cloud sessions already keep git credentials and signing keys outside the sandbox behind a proxy. Google’s builder is isolated from the people who run builds. A verifier still has to pin which signers it accepts.

    Tracekit, agentattest’s high-assurance level, Binary Authorization for Borg, and SLSA’s rule that consumers accept only specific signer and verifier pairs.

  5. A result the gate recomputes

    The gate must trust only its own code and inputs

    CI re-runs the tests. A reviewer outside the sandbox reads the diff again. Anthropic’s merge queue re-runs every check, and Claude Approvals leaves CI as its own required check.

    This repeats the work, which is the cost the goal wants to remove.

Inference Higher is not always better. Each rung costs time or setup, and the top rung repeats what the goal wants to avoid.

What a self-report is worth

Agents misreport and game checks, and the records show it.

Transluce found that a pre-release o3 “frequently fabricates actions it took” and justifies them when confronted. Anthropic describes reward hacking such as calling sys.exit(0) to make every test appear to pass, and notes it “has been documented in many AI models, including those developed by Anthropic”.

Passing a grader is not the same as being mergeable. METR had four maintainers judge 296 AI PRs that passed a SWE-bench grader, and their merge decisions ran about 24 points below the grader’s. Roughly half would not be merged.

Reviewers already ask for more evidence from agent PRs.

In a survey of 239 practitioners, 61.1 percent reported higher evidence requirements for AI-authored PRs, and the share who would block approval under residual uncertainty rose from 19.4 to 43.9 percent. The authors frame it as an evidence-ownership problem.

What the sources use to close the gap

  • Keep checks out of reach. Code Review reads REVIEW.md from the base branch. Claude Approvals reads policy from the default branch. A change that can edit the check that judges it makes the check broken.
  • Bind to the commit. Review results are reserved for commits. A passing review on an out-of-date commit “means nothing”. GitHub dismisses approvals when the diff or merge base changes.
  • Put the verifier outside the agent. Spotify’s agent does not see its verifiers. Tracekit’s signer is out of reach. Chainloop runs its gates in the pipeline.
  • Roll out as observe, then enforce, and sample. Anthropic runs new reviewers in shadow mode and samples a percentage of automated approvals. Claude Approvals and Chainloop both start report-only.
  • Ask for proof. Anthropic requires review agents to write a proof that a finding is valid.

Reviewing your own work

The evidence for independence is thin and mixed.

For independence: Greptile’s “a fox doesn’t guard the henhouse” argument, though it sells an independent reviewer. A benchmark of 14 open models reports that they fix errors attributed to others but miss the identical error attributed to themselves, and appending “Wait” cuts that blind spot by 89.3 percent. Another study finds that harmful self-preference persists when an evaluator erred as a generator. A single-team preprint reports low overlap between model families.

Against stacking: Anthropic says that adding a second, more expensive reviewer is often worse than tuning the primary, and that narrow-focus review agents “do not share biases and blindspots”. Its subagent reviews with fresh context. AI Control (2023) tests trusted editing and untrusted monitoring with measures to stop collusion. Practitioners on Hacker News split along the same lines.

Inference I found no study comparing the same model reviewing in the author’s sandbox with that model reviewing in CI. A fresh-context subagent addresses shared context, not shared training.

6How others avoid reviewing twice

Review is repeated for four reasons in the sources: every round starts from scratch, rounds have no cap, two places review the same diff, and an approval does not say what survives a new commit. Each pattern below answers one or more of them.

Build on earlier rounds.

Anthropic points each pass at context from earlier rounds rather than re-checking everything, which it calls cheaper and better at finding bugs. Cloudflare’s re-review gets its last comment and the review threads it posted. Fixed findings drop and their threads resolve. Unfixed ones are re-emitted so the thread stays open. Replies such as “won’t fix” count as resolved.

Fact
  • Anthropic, verification
  • Cloudflare

Re-review only the new diff, and cap the rounds.

Running git blame on what Anthropic’s reviewer kept flagging showed about 59 percent had been there since the first pass. The reviewer was finding a few more old bugs each round. Their fixes: a cap after three rounds, diff-only re-review after the first few passes, flag the class of bug, never repeat a posted finding. Stripe stops at one or two CI rounds and sends the branch to its human operator. This repo’s ENG-28 treats a blocking finding kept for three reviews with its file unchanged as stalled.

Fact
  • Anthropic
  • Stripe
  • ENG-28

Decide in advance which approvals survive a new commit.

GitHub can dismiss approvals when new commits change the diff, when the merge base changes, or require approval of the latest push by someone other than the pusher. Gerrit’s copyCondition keeps a vote across patch sets for chosen change kinds such as NO_CODE_CHANGE. SLSA requires that changes made during review are themselves reviewed. Anthropic: “a passing review on an out-of-date commit means nothing.”

Fact
  • GitHub rulesets
  • Gerrit labels
  • SLSA Source

Reuse results by content, and watch who can write them.

Bazel and Nx cache build outputs by an input hash: “as long as the input files remain the same, the output will be identical. So why build twice?” CREEP (CVE-2025-36852, severity 9.4) shows the hazard. A PR and main race to write the same cache slot, so an untrusted PR can poison what trusted builds read.

Inference A reused review answer is a cached build output. The same question applies to who may write answers and how an answer is bound to its inputs.

Cloudflare classifies each merge request as trivial (10 lines or fewer), lite (100 lines or fewer) or full, and sends security-sensitive files to full. Anthropic uses a classifier to pick a risk tier that sets how many people approve. Cursor scores risk to route PRs. Anthropic’s Code Review also scales agent count with the PR.

Anthropic: if an agent pushes before testing locally it has spent shared review and CI time it could have saved, so Claude runs tests, build and linter before opening a PR, enforced by a hook or a passing-suite goal. Stripe shifts feedback left. Spotify’s verifiers run before the PR opens.

After a change to the setup, the environment must be prepared again. The API reference lists a prepared revision, an active snapshot and a last-prepared time. I found no restore time, no expiry or refresh rule, and no statement on how a pull request that changes dependencies reaches a snapshot taken earlier.

Fact The agent’s own sandbox is a third case. Claude Code on the web lists docker, dockerd and docker compose among its installed tools and says to run your own image as a container beside Claude with docker compose. Replacing the base image is not supported yet, and the pages I read do not mention dev containers (cloud environments). In this session’s VM the docker and dockerd programs are installed and no daemon was running. I started none. CodeRabbit documents its CLI for Claude Code cloud environments: set network access to Custom, keep Claude’s default allowed domains and add CodeRabbit’s, which for the US region are cli.coderabbit.ai, app.coderabbit.ai and ide.coderabbit.ai (CLI network requirements).

Fact This repo has no .devcontainer folder, no Dockerfile and no container in a workflow. mise.toml pins its tools, and rust-toolchain.toml pins Rust 1.99.0, where CodeRabbit’s toolchain picker offers 1.84 to 1.86. Plan 2610031222 on sandboxed agents lists dev containers among the sandbox shapes its first task will survey. Inference No gate here needs a container today. In either vendor’s sandbox the repo’s exact tools would come from a setup script (CodeRabbit) or a pinned snapshot (Depot), not from a dev container image. I tested neither.

Fact Claude Code on the web has the same idea, described in the file-sharing table as the environment’s cache. Depot says its Sandbox SDK snapshots keep files, not running processes or memory, and Anthropic’s cache keeps files only. CodeRabbit starts the app from the startup script on every run. Inference I found no page that says any of the three keeps a running app, so the caches cover installation and not the app’s start or the checks themselves.

Depot runs checks on a delta. CodeRabbit judges a delta. Neither selects deterministic checks from it, and neither signs.

Inference Depot CI is the closest to the runner the owner described. It takes an uncommitted delta from the CLI, starts a job in 2 to 3 seconds and caches builds. The checks are the repo’s own, so they can be deterministic. The caller chooses them, each run is a command and not a stream, and nothing in the pages I read signs the result. CodeRabbit chooses checks from the delta itself, but a model does the choosing, and what comes back is a judgement: a review, scenarios it wrote, or a natural-language check. That suits a reviewer. It is also the one part of this repo’s gate that is not deterministic (section 8).

Both report to the forge as their own GitHub apps. A ruleset can pin a required check to one app, as this repo does for review-gate, which puts the check outside the agent’s VM. It does not say what the checked tree’s own code did, and the workflow file that names the checks is part of the tree the agent edits. Question 5 asks about this.

I found no feature in either product that declares which checks are the fast set. This repo has the start of one: scripts/ci-gates.txt lists CI’s gates once, and scripts/ci-local.sh runs the fast ones on the diff.

Fact the same split appears elsewhere. Linear starts workflows with a change-detection job that decides what runs next. VirtusLab’s guide runs only the tests a dependency graph marks as affected and warns that wrongly excluding a needed test is the dangerous failure. Apache Beam moves slow tests from pre-commit to post-commit.

Open questions

  1. What exactly is attested: a commit, a tree, a diff against a base, or a whole PR?

    GitHub binds approvals to the head and the merge base. Anthropic binds one approval to one commit. Occasio lists multi-commit attestations as an open question.

  2. Who signs, and can the agent reach the signer?

    Anthropic-hosted cloud sessions keep git credentials and signing keys outside the VM behind a proxy. Rulesets pin a check to an app. GitHub’s private-repository attestations federate only with Actions. I did not check whether this repo is public, which decides the Sigstore instance GitHub uses. ParleyInn’s own SRS leaves the same question open (OQ-40) and says the core’s keys do not qualify as a signer no agent can read.

  3. What does the gate recompute instead of trusting?

    Candidates that appear in the sources: the diff and its base, the tests, the reviewer definitions, the policy.

  4. Which checks must not move into the sandbox?

    Anthropic moves most review earlier and keeps a hard gate in CI. Cursor routes by risk. Claude Approvals reads policy only from the default branch.

  5. What happens when a PR changes the reviewers or the attestation format itself?

    “Changes can’t modify their own checks” against this repo’s own reviewer evaluation rules (ENG-32) and the PR’s agent instructions treated as data (ENG-28).

  6. Which results carry across a new commit, and when does an attestation lapse?

    GitHub, Gerrit and SLSA answer differently. This repo’s answer keys already say “unchanged key, any head”.

  7. What does the gate do with a missing or invalid record?

    Observe first and then enforce (Anthropic, Claude Approvals, Chainloop), or fall back to a full review in CI.

  8. How is the same quality bar shown to hold?

    ENG-32’s cases and stability measurement grade the reviewers. Anthropic also uses evals built from past incidents and a sampled human review of automated approvals.

  9. Where does the spend go?

    The 5 USD per-PR cap counts reviews in CI. A loop inside the sandbox needs its own cap. The sources show fifty-round runaways.

  10. What could the sandbox’s record leak?

    ENG-28 scrubs the OAuth token from everything uploaded. NovaFabric and Chainloop redact secrets in session records.

  11. Is the sandbox’s record ParleyInn’s own record, and where does a review result sit among its evidence classes?

    LANE-05 ranks claim, own check, witness check and CI attested. A witness check denies the network (OWN-18), so it cannot run a reviewer. LANE-08 says ParleyInn records no verdict toward landing and has no forge write-back. I found no class for a review verdict, and OQ-40 on who signs is open.

  12. Where does the validator’s key live, relative to the code it runs?

    A validator that runs the checked tree’s tests runs code the worker wrote, and SLSA Build L3 keeps the signing secret away from such steps. A second VM separates the two agents’ machines, not the key from the tree’s code. The sources put the signer outside the environment: Google’s isolated builder, Tracekit’s signer, Anthropic’s signing service for commits.

  13. Who starts the validating session, and what tells it which commit to check?

    Channels exist: messages, scheduled tasks that start a fresh session, and new project threads. I started no second session, so I do not know how long one takes to start or what it receives.

  14. Who decides which checks a delta needs?

    The sources show four ways. The caller names a job (Depot). A dependency graph selects the affected tests (Nx, Bazel, Pants and Gradle, through a remote cache). A change-detection job reads the paths (Linear). A model writes scenarios from the diff (CodeRabbit Verify). The dependency-graph guide warns that wrongly excluding a needed test is the dangerous failure. This repo already lists its gates once in scripts/ci-gates.txt.

  15. Who pins the review’s model, and does the record name it?

    CodeRabbit Cloud names no model per review and lets no one choose one. ENG-32 grades this repo’s reviewers on the model they run on. A signed review result that does not say which model produced it cannot be replayed or compared later.
