Question 1

Which key signs a result receipt?

Fact SEC-10: “The core MUST handle no credential other than its seat keys, the node’s device key and, until it leaves the node, its recovery key, on an ephemeral node the token key its access token carries…”. A CI key is not on that list.

Fact The model: a token key is one “a device key certifies by a token certificate… for an ephemeral node”, and “a node with only a token key signs no principal act”. A CI key is “a key the room’s owner enrolled in the room to sign CI attestations”.

Recommended

A. The node’s own key

The device key, or on an ephemeral node the token key. The receipt carries the token certificate, so a check walks back to a device key.

Model and SRS
No new key. SEC-10 already covers both keys.
Trust on GitHub
The default branch lists one device key per person. Every ephemeral node is covered by its token certificate, which expires with the access token.
Risk
The device key also signs principal acts. A fixed domain tag at the start of the signed bytes keeps a receipt from ever reading as one. A token key signs no principal act at all.
Other projects
Nothing to enrol beyond the device key they already have.
Possible

B. The editing run’s seat key

The key that seals the run’s writer signs the receipt.

Model and SRS
No new key, but a seat key “signs the seat’s room acts and seals its writer”. A receipt is neither, so the definition widens.
Trust on GitHub
A new seat key per run. GitHub still needs the chain up to a device key, so this adds a link and gains nothing.
Gain
Ties the receipt to the run’s writer, which an auditor can also get from a writer id in the receipt.
Rejected

C. A CI key

Enrol a CI key in the room and give it to the editing node.

Model and SRS
SEC-10 grows to hold a CI key in the core.
Effect
Its results would read as CI attested, the top evidence class, for checks run on the node the agent controls. That overclaims, and it puts the CI key where the threat model’s B3 can reach it.
Rejected

D. A new check key

A key kind minted per node or per release, only for receipts.

Model and SRS
A new concept in seats and keys, a SEC-10 change, and an enrolment act.
Effect
Separation that option A’s domain tag already gives. A key per release would be held by whoever builds the release, which signs nothing about a commit.

Judgement Take A. A result receipt is the node saying what it ran, so the node’s own key is the honest signer. The file on the default branch that phase 7 adds lists device keys; the check accepts a token key only through a token certificate from one of them, inside its expiry.

Question 2

Where does a result receipt stand?

Fact A receipt is “a signed statement about a node’s record, made to be kept apart from the home and checked with no network. Always qualified”: a head receipt or a purge receipt. The CLI has parinn head-receipt make|check.

Fact LANE-05’s closed set: claim < own check < witness check < CI attested. An own check is “a check capture recorded from the editing run’s transcript on that run’s node”, failing or passing by the tool result’s structural is_error. A witness check runs “outside any agent context”, by a node whose git identity authored no commit on the branch.

Recommended

A. A third receipt kind

A result receipt states, for one commit, the own-check results the node recorded, the digest of the parinn release, and the review outcome the review tooling kept.

Model and SRS
Receipt gains a third qualifier. It fits as written: it is about the node’s record, kept apart from the home, checked offline. LANE-05 does not change.
Evidence class
Each result stays own check, or claim when unbound. A verified receipt proves the signature and the digests, never a higher class.
Cost
To stay an own check, each check runs as a tool call of the editing run, so its exit status is a capture. The run can still start checks side by side.
Carried as
A git ref or a file beside the branch, like a bundle. It holds digests and exit statuses, no content.
Possible

A2. The same, and widen own check

The check script hands exit statuses straight to the core, not through the transcript.

Model and SRS
Own check’s definition and LANE-05 both change: a second, non-transcript source of a result.
Effect
Faster, one script run for all checks. But a source the transcript does not show is what the white-box view relies on to detect B2 and B3, so it weakens detection.
Rejected

B. A bundle, no new receipt

Export the run’s events in a bundle and let the job read the results from it.

Model and SRS
None.
Effect
A bundle carries record content to a public forge, and the job would parse the record format. Far heavier than the few lines a receipt needs.
Rejected

C. A CI attestation

Treat the verified receipt as CI attested.

Effect
Needs a CI key (question 1, option C) and overclaims. A new class between own check and witness check would change LANE-05’s closed set for the same reason.

Judgement Take A. The result receipt is a receipt like the other two, and its results are what they already are: own checks. What lets GitHub accept it on ordinary paths is the rule in ENG-16 and the file on the default branch, not a raised class. The review outcome it carries is engineering tooling (ENG-28) and is not a result.

Question 3

Are the GitHub action and the check script tooling or components?

Fact The component set is closed: “a new one is a model change and a §6.3 row”, while “how the components ship is open (OQ-32)”. OQ-32 still asks “whether the components ship as one executable or as one download of several”. The CLI is part of the core (B0). The launcher is “the only component that starts programs, but for the core’s own kernel worker”. ENG-29: no B1 to B3 component past a prototype without a decision record a named human security reviewer approves.

Fact Engineering tooling, in the model’s naming rules, is this repository’s own machinery (the review gate, answer keys, the size list). Nothing another project takes from a release is in that list today.

Judgement The action is the way a second project adopts ParleyInn: one uses: line, called by commit hash, and the locked parinn. That makes it something ParleyInn ships and keeps stable, which this repository’s tooling never promises. The check script is different: it starts programs, and only the launcher may do that among ParleyInn’s parts. The options below split the two along that line.

Recommended

A. The action ships the CLI; each project owns its check script

The action is a way the core’s CLI ships to a forge: it fetches the release of parinn named by its own version, checks the release signature, and runs parinn result-receipt check. The check script ships as a template that a project copies into its own repository and owns.

Model and SRS
No new component. OQ-32 gains a third shipping form beside one executable and one download. A new requirement makes the action a product interface: its inputs, its outputs, what it exits with, and that it is released and signed with parinn (ENG-20).
Other projects
Adoption is one workflow file, a list of checks and a list of keys on their default branch. ParleyInn keeps the action’s inputs, the receipt format and the list formats stable across a major version, with upgrade notes in the changelog (ENG-23).
Boundaries
The action runs only the core, offline; the release fetch is GitHub’s, before it. ParleyInn ships nothing that starts programs outside the launcher, because the copied script is the project’s own code.
Cost
Each project keeps its copy of the script up to date by hand until the launcher takes over.
Possible

B. Both are this repository’s tooling

The action and the script stay engineering tooling, like the review gate, and the release simply carries them.

Model and SRS
None.
Other projects
They would depend on something ParleyInn calls internal: no requirement covers it, no compatibility promise, no scenario proves it. Phase 9’s second project would be the first place a break shows.
Fit
Enough for dog-feeding in phases 3 to 7, short of what you asked for: an approach other projects can take.
Recommended later

C. The launcher starts the checks

parinn launch runs each check outside the agent context, and the copied script goes away.

Model and SRS
No new component; the launcher already exists. SEC-29 and ENG-29 apply.
Other projects
Nothing left to copy: the action and the launcher both come from the one locked release.
Cost
Waits for ENG-29’s decision record and its named reviewer. The launcher is off by default, B1.
Rejected

D. New components, or the bridge

A check runner and a receipt checker as new rows, or the action as part of the CI bridge.

Effect
New rows and an ENG-29 review for what the core and the launcher already cover. The bridge is B3, a network component off until turned on, and the check needs no network.

Judgement Take A, and plan C as the end state. The action is the adoption path, so it gets a requirement, a scenario and a stability promise like any other ParleyInn interface. The check script stays each project’s own code, which keeps ParleyInn from shipping a second program starter, until the launcher replaces it after ENG-29. Phase 9 then proves the promise with a second project.

Question 4

What are the subcommands called?

Fact The rule: a command on a concept is parinn <concept> <verb>, a multi-word concept in kebab case. verify is a node-wide utility: “chains, seals, the completeness of transcript sources, widening acts, and each derived artifact against a rebuild” (ADM-08). §9.5 lists about 80 commands today; none starts with a bare check.

Fact The model’s check is “a command executed, or expected to execute because one of the intent’s criteria names it”. The default branch’s list of checks is engineering tooling, not an intent’s criteria.

The concept’s name

Judgement The working name was “check receipt”. Its command parinn check-receipt check uses “check” twice in two senses, and the receipt does not state checks: it states results. The domain-model agent read the model for this and recommends “result receipt”; this page now uses it.

NameCommandFit with the modelVerdict
Result receiptparinn result-receipt checkIt states results, each with its evidence class, in the model’s own word. Its definition must say: only own-check results, plus the release digest and the review outcomeRecommended
Check receiptparinn check-receipt checkReads as a receipt for one check, and doubles the word. Easy to confuse with the forge’s required checksDropped
Commit receiptparinn commit-receipt checkNames the subject, not what is stated; reads as a receipt that a commit was recordedWeaker
Evidence, attestation or review receipt…Evidence is what a result rests on; attestation is the CI key’s word; review is an engineering-tooling wordRejected
Recommended

A. One concept, three verbs

  • parinn result-receipt plan <commit>: what a receipt for this commit must hold, from the default branch’s list, with each check’s command
  • parinn result-receipt make <commit>: sign what the record holds for it
  • parinn result-receipt check <file> [--json]: the offline checklist
Shape
parinn + concept result-receipt (the new receipt kind, kebab case because it is two words) + verb plan, make or check. A bare parinn receipt make --kind check does not fit, because the model says a receipt is “always qualified”; it would also have to move head-receipt and purge-receipt.
Effect
Everything lives under one concept the model gains anyway, with the head receipt’s verbs. No “record” verb is needed, since results arrive by capture.
Future
When the launcher starts the checks, plan and make keep their meaning; only who starts each check changes.
Possible

A2. parinn check list for the first step

What the first draft of this page proposed.

Effect
Opens a bare check concept in the CLI, and lists checks a repository file names, which the model’s check does not cover. It would claim the name before a later command on the intent’s checks needs it.
Rejected

B. Extend parinn verify

parinn verify --result-receipt <file>, or result-receipt verify.

Effect
verify checks this node’s own record. A file from another node, on a GitHub runner with no home, is a different job, and the head receipt already settled the verb as check.
Rejected

C. parinn attest …

A verb-first command.

Effect
Breaks the rule, and “attest” is the CI attestation’s word, which this receipt is not.

Judgement Take A. It adds one concept and one verb to §9.5, reuses the receipt family’s other two verbs, and leaves check free for the intent’s checks later. The domain-model agent should confirm plan before phase 3 names any function after it.
