1. **Managed-policy listings sit outside the record and key set, yet decide who is a person.**

  - The model (Managed policy, Service account) and PRV-10 let managed policy certify a service account by listing it, and revoke it by delisting.
  - A listing is a settings layer beside the record (record.md:11-14). It is not part of the key set, which is only "keys, certificates and revocations" (seats-and-keys.md:75-76).
  - No requirement records a listing.
  - So once delisted, the account "counts as a person's" (never certified). That contradicts "a service account whose certificate is revoked stays a service account" (model, OWN-27).
  - A node on another machine also sees the key as never certified. It would accept verdict pins this node refuses, which breaks LANE-22, LANE-31 and I10. The relaying mark that OWN-29 reads has the same problem, which breaks PRV-02's "deriving alike on all its nodes".
  - This is a question for the stakeholder.

2. **I2 has a dangling antecedent.**

  - "Under a delegation grant its principal recorded … for an agent of another principal" never names the delegating agent.
  - Read literally, "its" is the receiving agent, so for cross-principal delegation the receiving principal would record the delegation grant. That contradicts OWN-23 and OWN-26.
  - The fix needs new invariant wording, so an ADR and a security review. The trust-and-flow specialist shares this (Delegation grant).

3. **My file overstates I2.** It says "Only an agent's own principal widens what reaches that agent", but under OWN-26 the delegating principal's widening delegation grant is also required.

4. **"harness clear" rests on no requirement or assumption.** The model says it starts a new run. REC-02 and ASM-01 cover only harness resume, and nothing verifies that a `clear` carries a new `session_id`.

5. **§9.7.6 "solid for the agent's principal" has no clear referent** in a room with several principals' agents.

6. **02-context.md:38 "so runs can pause and resume"** uses the run-control words. The context (durable volumes) means a harness resume.

7. **LANE-28 traces I7**, but the commit hook is git configuration, not harness configuration. Harness configuration is "the harness's settings, hooks and MCP registrations", and harness-facts qualifies git's hook as the commit hook.

8. **The model's "A personal-room seat can neither leave nor be kicked" has no requirement.** LANE-23 and `room_leave` take a leave with no exception. Before PRV-10, LANE-25's owner protection does not clearly stop a kick of a run's personal-room seat. Either would contradict LANE-01's "else to its personal-room seat, never refused".
