## Record specialist: blind standing review, round 33 (HEAD)

I reviewed all of docs/srs/ (invariants.md included) and every features/*.feature file against docs/domain-model/record.md, the hub and the other model files. I listed all 70-odd concepts record.md defines and searched for each one, and for each word the hub excludes in its favour. That covers the import/ingest/receive exclusions and "work marker", and I found no use of either.

The model is internally clean:

- Each concept is defined once, and no other model file redefines one of mine.
- Every hub relation that names my concepts agrees with LANE-01, REC-19 and SEC-27.
- I1, I5 and I10 read the same in record.md, invariants.md and the cited requirements (REC-15, REC-17, REC-21, ADM-06/07/08, SEC-12, SEC-22, SEC-31, PEER-11).
- None of the findings below needs new invariant wording.
- Text marked open on OQ-39, OQ-40 or OQ-41 was not counted against anything unless it contradicts the mark. Finding 6 is outside OQ-40's list.

### Scenarios that cannot pass as written (needs-fix)

1. **features/record.feature:145 (REC-12).** A second fresh home ingesting the same transcript cannot have "the same writer id", and cannot derive "the same chain head hash".

  - The writer id comes from the seat's first key, which is generated on and bound to its node (SEC-10, REC-24).
  - The chained header holds the commitment (REC-10), which is made under a random per-event key (REC-17).

2. **features/record.feature:226 (REC-19).** The line says the core seals every writer except "the witnessed run's run seats'". That set includes the run seat `parinn ingest` starts. Line 222 of the same scenario, and the model's Seal entry, say the core seals that one.
3. **features/administration.feature:205 (ADM-15).** It has "a peer offers another event of that writer", refused with an audit entry only.

  - Peers exchange sealed ranges, not single events (PEER-03).
  - ADM-15 requires each refused segment to be recorded as REC-21 says. Line 206 does this; line 205 drops it.

### Contradictions and gaps for a ruling

4. **Integrity status per event.**

  - The model (record.md:152) and §9.7.5:98 define it for "a room or writer".
  - §9.3:122-123 says the envelope's `integrity` is "the integrity status of the event's writer".
  - VIEW-10, REC-18 and the RCL-09 scenario (recall.feature:127 and 133-134) give values per event. An event past the newest seal is `unsigned`, and an event after a break is `unverified` while its writer is `broken`. §9.7.5 itself defines `unverified` as "an event after a break".

5. **"key rotations" carry `structural`** (PRV-01 at 05-functional:46, record.md:75). Rotating a device key is a widening principal act (OWN-11, acts-and-roles, `parinn device-key rotate`), and OWN-02 records principal acts as `operator`. The class sits in the chained header and drives trust across nodes, so this is hard to undo once shipped.
6. **The peer component as a recorder.** SEC-25 (06-security:115) has the peer component record refused segments "as REC-21 says". ADM-15 and PRV-09 imply the same for received segments, including those the git carrier fetches. The closed recorder list and Origin's `witnessed` list (record.md:79-91) do not name the peer component or the publish component, and OQ-40 does not cover who seals what they record.
7. **Receipts "carry only digests".** SEC-19 (06-security:109) and §6.3 (06b:23) exempt head and purge receipts on the grounds that they carry only digests. SEC-31 makes the purge receipt carry the scope, the ranges and a list of copies, and sign it. The model calls every receipt "signed", which VIEW-10 and SEC-27 do not require for a head receipt.
8. **§9.1:27, the `Notification` row.** It says "ingestion (REC-13)", but REC-13 does not name Notification. The row's inputs carry no `transcript_path`, so recording notification text is not ingest in the model's sense.

### Term misuse (needs-fix)

9. **Unqualified "range" used for a sealed range** in PEER-12 (05d:28), §6.3 row 27 (06b:58) and peer.feature:136-137. In the model, "range" alone means an address range, and PEER-12 itself uses "address ranges" in the same row for a different thing.
10. **REC-17 (05-functional:32)** names the commitment key only as "`k_e`, a random per-event secret". REC-23, ADM-07 and the model call it the commitment key.

### Places where record.md does not match the requirement it cites (questions, since the fix is in my file)

11. **Payload (record.md:44-45).** The model says "a name that confirms no guess at its content". REC-09 only requires that no one off this node can confirm a guess.
12. **Flag (record.md:138-139).** The model flags any event. PRV-07 flags only untrusted events.
13. **record.md:76, "a witness check's record".** This gives "record" a second meaning, an event, beside the Record concept.

### Instruction feedback

- **Kind for a mismatch fixed in my own file.** It was unclear which kind to use when record.md disagrees with a requirement it cites and the requirement is plainly right (items 11 and 12). "Outside a change to your file, report ... as a question" suggests "question", but the fix is a wording alignment with no new concept. Please say which kind applies.
- **"Each concept file your file points to."** record.md has no links to other model files; it only uses their concepts. I read all nine. Please say whether that is expected.
- **"Where to start" misses files that carry most of record.md's concepts:**
  - docs/srs/08-data-and-storage.md (store, payload store)
  - docs/srs/09-interfaces.md (address forms, envelope `integrity`, restore-block landmarks, §9.1 ingest)
  - docs/srs/09a-command-line-interface.md (export, import, purge, receipts, backup)
  - docs/srs/09b-lane-vocabulary.md (§9.7.5 integrity status)
  - docs/srs/05d-peer-requirements.md and features/peer.feature (segments, sealed ranges, missing ranges)
  - features/lane-view.feature (VIEW-08/10/11)
- **"Writer" as an actor.** The model defines a writer as a log, yet the model (trust-and-flow, Fork: "one writer sealed") and the SRS (REC-06 "assigned only by that writer", ENG-09 "50 concurrent writers") also use it as an actor. I treated this as accepted usage, not a finding. A line in the instructions on whether such usage is in scope would help.
