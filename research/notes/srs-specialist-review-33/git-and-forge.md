### Findings, most important first

1. **"Head" is undefined, and two scenarios treat an uncommitted edit as a head change.** My file uses branch "head(s)" without defining it (lines 52, 74, 82). OWN-21 and OWN-27 react only to a change of a branch head (or, for OWN-27, the intent version or evidence). In git's sense a head is the tip commit. Yet the OWN-21 scenario ("the agent then edits the worktree … returns to Running or Quiet until marked again") and the OWN-27 scenario ("the agent then edits a file … the verdict reads stale") both expect an uncommitted edit to have that effect. This is a question for the stakeholder: do uncommitted worktree edits make a verdict stale and clear a ready mark?

2. **My file's definition of "tree" contradicts Own check and LANE-05.** My file defines a tree as "git's snapshot of a commit's files". But an own check runs on "the latest worktree checkpoint plus the recorded edits" (LANE-05: "the tree is the latest worktree checkpoint plus the edits recorded since"). That is uncommitted state, not any commit's snapshot.

3. **LANE-20 does not say what my file cites it for.** My file says "A check is expected when one of the intent's criteria names its command (LANE-20)". LANE-20 only says "a criterion MAY name a check's command". Only the model and a step of the LANE-20 scenario (lane.feature:293) state the "expected" rule, and nothing normative backs the Pending/Absent check states.

4. **My file states as permanent something OQ-37 leaves open.** My file says "ParleyInn never lands anything" and "It approves and lands; ParleyInn does neither". OQ-37 still asks "May ParleyInn run, push or merge code itself?", and the current rule holds only "until this closes". This is a question.

5. **The LANE-08 scenario title overclaims.** It says "each branch of the room carries a pull-request link". The steps and LANE-08 give a pull-request link only to a branch that has a pull request.

6. **The LANE-06 scenario gives the proof class to the room.** The title says "the rooms behind a landed commit carry one proof class" and the step says "the room is listed with proof class". A proof class belongs to a landing link.

7. **"Check" is used in other senses in normative text.** LANE-26 says "refused by the check of LANE-16". The OWN-12 scenario says "refuses before any other check". SEC-07 and its scenario speak of a "static check" and say "the check fails". In the model, a check is a command run on a tree.

8. **"Evidence" is used in another sense in normative text.** SEC-01, SEC-19 and ENG-12 speak of "build-time (reach) evidence" and "that evidence". Their scenarios say "a component's evidence" (security.feature:10–14, 236, 362; engineering.feature:142). In the model, evidence is what a result rests on.

9. **NFR-15 and its scenario say "replay rebuilds a worktree".** A worktree is a git working tree on a node, which ADM-13 bars ParleyInn from writing, and "rebuild" is `parinn rebuild`'s word. VIEW-12 says "reconstruct".

10. **The keymap says "compare versions".** That uses the comparison's verb for an intent-version diff. In the model, "choose a branch to compare" belongs to the comparison of two branches.

11. **Persona U5 names an evidence class "CI".** "claim versus own check versus CI" uses a name that is not the class's name and leaves out witness check.

12. **Non-normative prose uses evidence, result(s), comparisons, checks and tree in other senses.** This is one grouped, low-weight item covering the assumptions register, the rationale, ADR rationale cells, §11, Appendix A and assumptions.feature. Locations are in the JSON.

13. **My file's summary attaches proof classes to results.** It says "results with their evidence and proof classes", and the hub catalog row repeats it. Proof classes belong to landing links. This is a question.

14. **For the record specialist:** record.md:160 uses "tamper evidence", a second meaning of my Evidence concept.
