# Why the core findings survived the earlier rounds

The strong reviews of the original model text (the selection search, 8 October
2026) kept reporting about fifteen needs-fix themes. Four agents traced each
through the 32 blind review rounds, the persona rounds, the stakeholder
walkthrough and the git history of `docs/`. The full traces, with evidence
(file:line and commit shas), are in `core-findings-history.json`.

## Causes

- **The lens.** Rounds 1 to 32 followed the domain-model agent's brief:
  terms, relations and drift between the model and the SRS. Their reviewers
  read the SRS beside the model, so a rule the SRS states and the model
  omits showed no drift. From round 28 the adversarial step checked that
  findings were accurate; it never attacked the rules. The search's
  reviewers read the model alone, with a security lens and a "gap" type.
- **Decisions landed in the SRS.** Several themes were settled, but in a
  requirement or a residual-risk row, not in the model entry the rounds
  edited.
- **Local fixes.** Each round's skeptics checked that round's edits only, so
  a blanket rule added for one question contradicted another entry (access
  token expiry, which pin version restores, revocation classes).
- **Silent cuts.** Trims to keep the single-file model under its token limit
  dropped rules without a recorded decision (the git carrier's owner, the
  expire-act recorder).
- **The rounds never converged.** Each round ended with 8 to 24 needs-fix
  findings; round 32 ended at 8 when the stakeholder stopped it.
- **The repair phase fixed most of them, in copies.** v1 to v6 of this
  search wrote fixes for A, C, D, E, I and O, but the selection-only ruling
  kept them in `annotated-v*/`; `docs/` never received them.

## Per theme

- **A. An agent's own `parinn` call acts as the device seat or passes "at a terminal".** The same-user-agent risk was raised and settled before the model existed (persona rounds 4-7, OQ-29): accepted as residual risks R1-R7 and parked in an unstarted sandbox plan, with the SRS saying so, but none of the entries the 32 rounds edited carries that. The rounds used a consistency-and-drift lens (.claude/agents/domain-model.md), so they classified "at a terminal" and "wherever it is taken" without asking who could satisfy them. The v2 room-act/principal-act split also moved device-seat acts such as post out of OWN-12's terminal rule, and the SRS scopes the same-user threat to principal acts only, so ParleyInn's own `parinn room post` as the device seat falls outside both the control and the accepted-risk list. The repair phase showed that ancestry tests breed new bypass findings while one boundary sentence quoting the SRS risks quieted the probes, but that text was never merged.
- **B. Ownership, admission and bars rest on principal-key chains that do not exist before PRV-10.** The general question was never asked. Five separate 'before PRV-10' questions (signing, expiry, pin restore, recorder, seat kind) were each closed with a local parenthetical, which made the model look hedged while the definition of counting principals by chain and its consumers (owner protection, admission, invites, bars, delegation to another of one's nodes) stayed unconditional. The rounds' reviewers worked from the domain-model agent's brief (terms, relations, model-versus-SRS drift; .claude/agents/domain-model.md:30-48) and were partitioned from R22 so Principal (principals-and-agents) and Bar/Admission (acts-and-roles) sat with different reviewers. By 12-delivery-plan.md:50 PRV-10, LANE-23..33 and the P1 OWN rows all ship in M7 and peers in M8, so the pre-PRV-10 window may hold no second principal at all; that is my inference, and the model nowhere says it, so a model-only reader sees a gap. The fix text exists only in research/ and was never applied.
- **C. Revoking a seat key or access token is cut; revoking a device is widening.** Round 15 decided the right thing (widening when it stops a pin restoring) but wrote it into SEC-27 and the CLI table, not into the model's Cut list, and the SRS's own OWN-11 lost the entry in c4ea643. Round 21 saw the leftover and triaged it as optional; round 27 then added a widening reason ('drop pins and stop acts arriving') that covers seat-key and token revocation too, so the fix moved the problem. The seq a revocation stops at was never asked because the 32-round reviewers read the model against the SRS, where PRV-10 supplies a rule; the October reviewers saw the model alone. The repair-phase rulings that did fix it never landed in docs/.
- **D. A run-seat key lost with its MCP server.** The 32 rounds' reviewers (the domain-model agent, whose job is concept and term fidelity) never asked what happens to the key when the process holding it ends; each round that touched run seats answered a neighbouring question (who seals ingest's appends, which server holds a subagent's key, whether a forked resume is a new run). The one adjacent question that was raised was parked on ASM-21 and spike S4, which does not cover it, so the deferral had no owner. Nothing in the SRS covers restart either (SEC-10, REC-19, REC-18 'unsigned' fallback only). The fix existed in the repair phase but was discarded with that phase's text.
- **E. Which runs are one agent.** Four rounds (4, 9, 17, 26) added rules that quantify over 'the agent', yet no round asked what an agent is across runs, because the question that was asked and answered was the run's identity (R22 Q3), which made the gap look closed. The domain-model reviewer checks terms are defined, and 'agent' is defined; the missing piece is behavioural (equivalence of runs), which only the October implementer-divergence lens ('two careful implementers build different things') flags. Where the rulings that answer it were written (repair F5/F6), F5 conflicted with the SRS and none landed.
- **F. Untrusted `.parinn.toml` may "tighten"; configuration pins without acceptance.** The configuration-pin half was raised by the persona security review and settled in the SRS (ADM-04 since 966c80d: acceptance with a recorded digest, repository keys ignored, audited and counted), but the 32 model rounds only touched the vocabulary (naming repository configuration, settings layers, retention) and never copied the rule into the Configuration pin entry. The model cites ADM-04 for "tighten" while the per-key meaning is in SEC-11 and §9.6, and the v0 reviewers, who by brief cannot read the SRS, see an undefined word and an untethered pin. The one real design conflict, §9.6 letting a repository lower the pin budget or turn restore off against the model's widening rule and I3, was never raised, and the v5 repair that forbade it contradicts the SRS table.
- **G. Access tokens cannot expire before PRV-10.** R20 introduced a blanket 'no expiry before PRV-10' as the answer to another question. R30 then listed access tokens among the things an expire act ends in the same sentence, and R31 carved out exactly one exception (grants) and stopped, because that decision was about delegation. The text that makes access tokens expire (Access token, PEER-06's mandatory expiry) sits in a different file read by a different reviewer, and each round's skeptics checked only that round's edits. The decisions R30 and R31 are carried in the current text; what is missing is any rule for access tokens before PRV-10. By the delivery plan PEER-06 (P2, M8) follows PRV-10 (M7), so the conflict is probably latent rather than live (my inference), but the model does not say so.
- **H. Which node records the expire act ending a bar or mute.** The model once held a recorder cascade; round 9 dropped it from the model without a recorded decision, leaving a pointer to LANE-25. Every later reviewer read the SRS next to the model, found LANE-25's cascade and agreed (SRS review 33: 'Expire acts agree with LANE-25, PEER-05, OWN-23 and OWN-26'), so the omission was invisible to them. The GA reviewers read the model alone (eval-brief.md:11-13) and with a security lens (eval-brief.md:36-39), which is what shows that nothing stops the muted party's own node. Even the SRS rule is a permission with no validity condition, a point no round examined because the rounds' brief checked terms and drift, not attacks.
- **I. Pin-candidate confirmation without the exact text shown.** Every round settled who confirms a pin candidate, in which act class and as whose pin, but a drift-and-consistency reviewer finds places where two texts disagree, and here the model and the SRS are both silent on what the principal is shown. The neighbouring exact-text rules for stamp, endorsement and the intent candidate made the gap look covered, and pin candidates never appeared in any persona report, UX design or proposal row. The security lens that finds omissions first ran on 8 Oct. The one-clause fix (v1 R16) closed it in a research copy that was discarded.
- **J. Every room view client is reduced.** J mostly is not a defect that survived 32 rounds: in the full text the browser is the one non-reduced client, and the finding appears only in candidates assembled without browser-room-view while the "as reduced clients" phrase stays in core. No domain-model round could have seen it, because every round reviewed the full text, and the v1 repair already fixed the span placement. A weaker form remains in the full model (the one full client is optional and no sentence says some client must show every surface), but no review of the full text has reported it.
- **K. Which pin version restores, and must its event be trusted.** The round-3 decision was applied, but in a place (the post-PRV-10 clause) that left a pre-PRV-10 hole, and the later per-version-authorship decisions (R10, R12) invalidated the SRS's single 'creating event' condition, which R23 then copied into the model as a no-decision fix. Each later round patched a special case (intent, non-restoring types, foreign room) rather than stating once which version restores and that its own event must be trusted on the node. The 'missing from Trusted sources' part of the theme is not a defect of the current text.
- **L. Service-account certificates without consent; listings outside the key set.** Every step of the certification design was an explicit, recorded decision that the current text carries faithfully, and no round examined the combined result as an attack or against I10; the rounds' brief was terminology and drift, and the 'adversarial check' of R28-R32 verified findings for accuracy (blind-28.md:6-9), it did not attack rules. The I10 half was first caught by the SRS review of round 33 (C20, classed 'decide', status 'bundled, not yet applied' until the subset search settled the core), so it never reached the model. The consent half was never raised before the GA/SA security lens. R30 Q10's wording suggests the listing is in the key set, but no model text says so, so that decision is only half written.
- **M. Two rooms naming one branch.** Two raw reviewers asked in rounds 6 and 7 for the missing 'branch belongs to the first room' clause, but the merged note kept only the tie-break half as a no-decision fix and the other half vanished without a decision, deferral or OQ. Every later reviewer read the SRS beside the model, where LANE-01, LANE-28 and lane.feature:22 settle it, and their prompt asked only for contradiction, undefined term, drift and wording, so a model sentence that is a thin copy of an SRS rule showed no conflict. The GA/SA reviewers saw only the model text (research/notes/domain-model-subset-search/eval-brief.md: 'Review ONLY this text. Do not read ... docs/srs/') and had a 'gap' type, so the missing scope became visible there (4 hits, 1 needs-fix).
- **N. Who enables the git carrier, on which remote, within which visibility.** The who and per-remote decision was made in round 7 and written into the model, then cut ten rounds' worth of text later in a word-trimming pass that brought the single-file model back under its 12,000-token limit; no review note records the cut. Because PEER-08, ADM-13 and peer.feature:89 still state it, later reviewers who read the SRS beside the model saw no drift, and when round 26 added the carrier switch to Room merge the owner attribution given to the CI key was not given to the switch. The visibility limit was never raised in 32 rounds because round 16's rule named only publish and blind peers; round 33 raised it but parked it behind the subset search.
- **O. Quota reached; backup not classed as a principal act.** Both halves are settled in the SRS (ADM-15 and 09a:111-113, ADM-06) and the model entries cite those ids, so reviewers who read the SRS beside the model saw no drift; every edit to Quota and Backup in 32 rounds was about names, scope or contents. The review prompts asked for contradiction, undefined term, drift and wording against the SRS, with no 'gap' or 'security' type and the SRS in view, so 'what happens at the limit' and 'is copying the whole store a widening act' never counted as defects. The one drafted model fix for the quota effect (repair R15) stayed in the research copies after the selection-only ruling, and the backup-create decision was taken on the recommended option without the I8 and export-review-step argument the GA/SA reviewers later made.
