# Own the record and its keys; let git and chat be opt-in views that shred by key

ParleyInn should own its storage and its keys, but not the network, and it should not become a forge or a chat server. Nothing live combines a git interface, a chat interface and crypto-erasure on one storage layer. Keybase did, with a go-git remote helper over encrypted KBFS and exploding messages whose keys are deleted on a schedule, but it has been frozen since Zoom's 2020 acquihire. Block's Buzz comes closest among live projects: one signed Nostr log for messages, reviews and git events, a room per branch, and agents with their own keys. But it is Rust, Postgres and Redis, the operator can read it, and it deletes only on the relay. The parts exist separately. The 2026 git engines (Cursor Continuity, Entire, Cloudflare Artifacts, GitLab's next-gen SCM, ERSC) show git's wire protocol can sit in front of a log you own. Keybase and git-remote-gcrypt show encryption fits *below* git, and go-git v6 can serve git over a pipe. Matrix shows a hash-linked event graph can survive content removal if the hash covers the redacted form. Crypto-shredding is routine in event sourcing, but the EDPB's final blockchain guidelines (v2.0, 7 July 2026) do not accept key deletion alone as erasure. They treat encrypted data as personal data and advise keeping it, even encrypted or hashed, off an immutable ledger, while accepting keyed hashes, commitments and tombstones. The design that falls out has five rules. The chain commits to keyed hashes of ciphertext envelopes, never to unsalted content hashes. Each session or data subject gets its own data key, kept outside the record. Shredding destroys the key, deletes the ciphertext and appends a signed tombstone. Git and chat are separate opt-in processes outside the I4 binary. Copies that reached a bridge, the model provider or someone else's clone cannot be shredded. One finding reaches back into v1: the SRS's purge keeps an unsalted SHA-256 of removed content, which lets anyone holding the record confirm a guessed short secret.

This report follows [Agent session storage beyond git](agent-session-storage-beyond-git.md), which set the direction: code stays on git, ParleyInn owns a per-origin tlog-tiles record with signed checkpoints, and carriers stay outside the binary. The deciding invariants are in [the SRS introduction](../../docs/srs/01-introduction.md): I2, I4, I6, I8 and I10. Every external claim cites a source from the four research notes. Inferences are marked.

## Nobody combines git, chat and erasure today

The three properties have shipped together exactly once. Integrated systems sort into four groups ([Keybase chat crypto](https://book.keybase.io/docs/chat/crypto); [block/buzz](https://github.com/block/buzz); [Radicle protocol](https://radicle.dev/guides/protocol); [any-sync](https://github.com/anyproto/any-sync)):

1. **Git, chat, end-to-end encryption and shredding:** Keybase only, now in maintenance.
2. **Git and chat, signed, operator-readable:** Buzz, Zed Delta, Fossil, and Forgejo with a Matrix webhook.
3. **Git and asynchronous discussion, signed, peer-to-peer, plaintext at rest:** Radicle, Tangled and NIP-34.
4. **Encrypted chat with no git:** Keet, any-sync (Anytype), Peergos and SimpleX.

The agent-first entrants of 2026 sit in group 2. A security-first, shreddable store with both interfaces would sit in a quadrant nobody occupies. That last point is an inference from the grid.

### Keybase did it once, and it is frozen

Keybase gave each user one identity with a signature chain and each device its own keys. Chat reuses the symmetric key of the matching private KBFS folder, and removing a device makes the others share a new key, so "the removed device can't read new messages" ([Keybase chat crypto](https://book.keybase.io/docs/chat/crypto)). Encrypted git was `git-remote-keybase`, built on go-git over a crypto storage layer that "doesn't really understand git". The server could not see repository names, branch names or contents, but did see team membership, devices and who pushed ([Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone)). Concurrent pushes over a synced filesystem gave "a conflicted HEAD", so git got its own locked layer ([Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone)).

Deletion was two-tier. Normal messages have no forward secrecy: "the keys to read them still exist on your devices, and they never get deleted" ([Keybase chat crypto](https://book.keybase.io/docs/chat/crypto)). Exploding messages are real crypto-shredding. Each device makes a daily ephemeral keypair, "keys are deleted one week after the following generation is issued", and a device silent for three months goes stale, so "one mothballed device won't compromise the forward secrecy of an entire group forever" ([Keybase exploding messages](https://book.keybase.io/docs/chat/ephemeral)). Under KBFS, block IDs hash *encrypted* blocks, and deleting a server-held per-block key half shreds the block ([KBFS crypto spec](https://book.keybase.io/docs/crypto/kbfs)).

Zoom acquired Keybase on 7 May 2020 and said it would not continue the product as it was ([Decrypt](https://decrypt.co/28121/keybase-users-revolt-following-zoom-acquisition)). The latest client release is v6.6.3 from 3 June 2024 ([keybase/client releases](https://github.com/keybase/client/releases)). An April 2026 opinion blog describes servers still running and keybase.pub taken offline "abruptly" in March 2023 ([schulz.dk](https://schulz.dk/2026/04/06/the-cryptographic-zombie-how-keybase-went-from-privacy-darling-to-zooms-cleanup-crew/)). No end-of-life notice was found. The licence is recorded as BSD-3, not re-verified. The lesson is organisational: a single company holding the identity and key system can be bought and frozen.

### Buzz and Delta joined code and conversation, and dropped encryption

Block launched Buzz as an open-source, Apache-2.0 workspace for humans and agents ([SiliconANGLE](https://siliconangle.com/2026/07/21/block-launches-buzz-open-source-workspace-humans-ai-agents/)). "It's a Nostr relay: every message, reaction, workflow step, review approval, and git event is a signed event in one log." The relay is Rust, with Postgres for events and search, Redis for pub/sub and S3 or MinIO for media ([block/buzz](https://github.com/block/buzz)). Agents hold their own keys, a second signature binds each to its human owner, and `buzz-acp` drives Claude Code, Codex and goose ([VISION.md](https://raw.githubusercontent.com/block/buzz/main/VISION.md); [SiliconANGLE](https://siliconangle.com/2026/07/21/block-launches-buzz-open-source-workspace-humans-ai-agents/)). Its "branch as room" model is the closest match to the stakeholder's idea: a feature branch opens a channel, patches land as NIP-34 events, and "the merge decision lands in the same room as the evidence" ([block/buzz](https://github.com/block/buzz)).

Buzz is not end-to-end encrypted: "TLS in transit. At-rest encryption delegated to the storage layer (e.g., Postgres TDE, volume encryption)" ([VISION.md](https://raw.githubusercontent.com/block/buzz/main/VISION.md)). NIP-44 is "not implemented", and NIP-17 gift wraps are stored "community-globally" ([NOSTR.md](https://raw.githubusercontent.com/block/buzz/main/NOSTR.md)). Deletion is NIP-09 kind 5, plus kind 9005 for admins, committed with the removal in one transaction ([ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)). Nothing is crypto-shredded. Its SHA-256 hash-chained audit log is fire-and-forget: a failed audit write does not fail the event ([ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)). Under I6 that would be a silent failure.

The sources disagree on Buzz in three places. SiliconANGLE dates the public launch to 21 July 2026, while one blog says it "launched March 6, 2026" and shipped v0.5.18 on 21 August with about 30k stars; the March date may be the first commit ([SiliconANGLE](https://siliconangle.com/2026/07/21/block-launches-buzz-open-source-workspace-humans-ai-agents/); [carlos.lat](https://carlos.lat/en/blog/buzz-block-workspace-2026/)). One fetch of the README listed git hosting and the desktop app as "being wired up", a later one as "Works today" ([block/buzz](https://github.com/block/buzz)), and reviewers call the git side "the least mileage" ([mager.co](https://www.mager.co/blog/2026-07-24-buzz-explainer/); [TFTC](https://www.tftc.io/buzz-block-nostr-ai-agent-workspace-launch)). NOSTR.md omits NIP-34 while the README and VISION include it ([NOSTR.md](https://raw.githubusercontent.com/block/buzz/main/NOSTR.md)). The README warns: "Please do not plan your compliance program around the 💭 column yet" ([block/buzz](https://github.com/block/buzz)).

Zed announced DeltaDB on 11 June 2026 and opened the Delta public beta on 16 September ([Zed blog](https://zed.dev/blog)). DeltaDB gives each operation a stable identity, and "a message and the edit it produced are recorded side by side" ([Introducing DeltaDB](https://zed.dev/blog/introducing-deltadb)). It "works with the git repository you already have" ([Introducing Delta](https://zed.dev/blog/introducing-delta)). Encryption, licence, erasure and self-hosting are not documented ([Delta public beta](https://zed.dev/blog/delta-public-beta)). Entire's Go CLI stores sessions under `refs/entire/checkpoints/<shard>/<id>`, calls its redaction "best-effort" and mentions no encryption ([Entire README](https://cdn.jsdelivr.net/gh/entireio/cli@main/README.md)). The market has converged on linking code to conversation. Security has not followed.

### Everything else covers one or two of the three

Radicle signs refs per peer and carries issues and patches as git commit DAGs, but "the data is not encrypted at rest" ([Radicle protocol](https://radicle.dev/guides/protocol); [Radicle FAQ](https://radicle.xyz/faq)). On Tangled's AT Protocol, "all data stored on the protocol today is public" ([atproto Spaces](https://atproto.com/blog/atproto-spaces-alpha)). A fetch summary claimed Tangled supports encrypted private repositories; the note writer could not verify it and treats it as unreliable. NIP-34 puts patches and issues on Nostr relays, while git objects stay on ordinary git servers ([NIP-34](https://github.com/nostr-protocol/nips/blob/master/34.md)).

On the encrypted side, any-sync is a Go, MIT library for end-to-end-encrypted DAGs with ACLs that powers Anytype's chat, with no git interface ([any-sync](https://github.com/anyproto/any-sync)). It shows the cost of user-held keys: "Anytype cannot recover a lost Key" ([Anytype data erasure](https://doc.anytype.io/anytype/data/data-erasure-and-recovery.md)). Peergos runs chat on an encrypted filesystem whose server "doesn't even know you're sending chat messages" ([Peergos chat](https://peergos.org/posts/decentralized-chat)). Fossil's chat messages "do not sync to peer repositories" and are "automatically deleted after a configurable delay (default: 7 days)" ([Fossil chat](https://fossil-scm.org/home/doc/trunk/www/chat.md)). Forgejo's link to Matrix is a webhook ([Forgejo matrix.go mirror](https://git.fb1.uni-bremen.de/davrot/forgejo_backup/src/branch/upload_with_path_structure/services/webhook/matrix.go)), and its own Matrix room was abandoned after "state resets which are a known bug in Matrix" ([Forgejo report](https://forgejo.org/2025-05-monthly-update/)).

## Git works as an interface over storage you own

The git half of the idea is the best supported. In 2026, every agent-scale git engine kept the client protocol and replaced what sits under it. None of them owns the keys, though, so the encryption and erasure half has to come from elsewhere.

### Every 2026 engine keeps git's protocol and replaces the storage

Cursor's Continuity engine, behind its Origin forge, makes a write-ahead log in S3-compatible storage the source of truth. Each node keeps "a normal Git repository stored on a very fast NVMe drive" as a warm cache rebuilt from the log. Pushes are linearised by compare-and-swap on S3, and "we never acknowledge a push until it has been fully persisted". Replicas learn of changes by UDP gossip and confirm with a conditional GET ([Cursor blog](https://cursor.com/blog/git-at-any-scale)). Encryption, erasure and licensing are not addressed, and it is not open source.

Entire's network has "a global control plane for identity and placement, and regional data planes for content-addressed Git storage", where "ref updates remain protected by compare-and-set semantics", and a remote helper serves `entire://` URLs ([Entire blog](https://entire.io/blog/an-entirely-new-git-hosting-network)). Encryption and deletion are not documented. Press coverage is dated 8 July 2026, but the blog post is dated 28 August with an editorial note ([SiliconANGLE](https://siliconangle.com/2026/07/08/ex-github-chiefs-entire-opens-distributed-git-network-agent-era/)).

Cloudflare Artifacts, in beta since 16 April 2026, keeps each repository in a Durable Object with SQLite, implements git in about 100 KB of Zig compiled to WASM, speaks protocol v1 and v2, and uses git-notes for agent metadata ([Cloudflare blog](https://blog.cloudflare.com/artifacts-git-for-agents-beta/)). It is "nearing 50,000 new repositories per day" ([Cloudflare product page](https://www.cloudflare.com/products/artifacts/)), and its docs say nothing on deletion or encryption ([Cloudflare docs](https://developers.cloudflare.com/artifacts/)). GitLab's next-gen SCM promises "a different motor underneath" with "same Git compatibility", but its 10 June 2026 announcement gives no storage design, and the brief's "August 2026" date has no primary source ([GitLab blog](https://about.gitlab.com/blog/gitlab-transcend-announcements/)). ERSC is building a server that "speaks git and 'jj'" for "thousands of commits per second", in early trial with no architecture or licence published ([ERSC blog](https://ersc.io/blog/ersc-availability)). Its CTO announcement is dated 8 July 2026 by one source and 2 September by another ([ecosistemastartup](https://ecosistemastartup.com/?p=103676); [byteiota](https://byteiota.com/git-hits-its-ai-ceiling-ersc-bets-on-whats-next/)).

The engines converge on one shape: an immutable log or content-addressed store as truth, compare-and-swap on refs for many writers, and a local git repository as a disposable cache. That is the same bet ParleyInn makes with an append-only record and rebuildable projections under I10, and Continuity is the most explicit design to borrow from. None publishes customer-held keys or crypto-erasure. These are inferences from the table.

### Remote helpers give git a front door without a socket

When git meets a URL scheme it does not know, it spawns `git-remote-<scheme>` and talks a line protocol over stdio. No listening socket is needed. This is the lightest way to keep `git push` and `git fetch` while owning the storage. Every serious system above uses it: `keybase://`, `rad://`, `nostr://` and `entire://` ([Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone); [Radicle protocol](https://radicle.dev/guides/protocol); [NIP-34](https://github.com/nostr-protocol/nips/blob/master/34.md); [Entire blog](https://entire.io/blog/an-entirely-new-git-hosting-network)).

git-remote-gcrypt is the closest design to per-key shredding. It encrypts each packfile under its own key and signs and encrypts a manifest of refs to listed GPG participants. But "every git push effectively has `--force`", repacking is unpredictable, and the licence is GPL-3.0 ([git-remote-gcrypt](https://github.com/spwhitton/git-remote-gcrypt)). awslabs' git-remote-s3 locks each ref with a 60-second TTL and leaves encryption to S3 or KMS ([git-remote-s3](https://github.com/awslabs/git-remote-s3)). git-remote-ipld was archived on 31 July 2026 ([git-remote-ipld](https://github.com/ipfs-shipyard/git-remote-ipld)).

Three inferences follow. GPL-3.0 is off ParleyInn's allow-list (Apache-2.0, MIT, BSD, ISC under [ENG-18](../../docs/srs/10-engineering-quality.md)), so gcrypt's design can be reimplemented but not vendored. Implicit force-pushes and lock TTLs show that a helper over a dumb store is weak with many writers; compare-and-swap on a ref log is safer. And because repacking merges packs, key granularity must ensure a repack never re-encrypts shredded data under a live key.

### go-git v6 can serve git in-process, if its import closure is clean

go-git is the main pure-Go option and is Apache-2.0. v5's `plumbing/transport/server` serves upload-pack and receive-pack over any storer; v5.19.2 shipped on 29 July 2026 ([go-git v5 server](https://pkg.go.dev/github.com/go-git/go-git/v5/plumbing/transport/server)). v6 separates the transport abstraction from concrete transports, supports protocol v2, and exposes `UploadPack()`, `ReceivePack()` and `AdvertiseRefs()`, with SSH, HTTP and file transports in their own subpackages ([go-git v6 transport](https://pkg.go.dev/github.com/go-git/go-git/v6/plumbing/transport)). Keybase proves go-git runs over encrypted custom storage ([Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone)). soft-serve, gitkit and Gitea all shell out to the git binary ([soft-serve](https://github.com/charmbracelet/soft-serve); [gitkit](https://github.com/sosedoff/gitkit); [Gitea cheat sheet](https://docs.gitea.com/administration/config-cheat-sheet)), and `os/exec` is banned in ParleyInn's shipped code.

Protocol v2 has the hooks a custom server needs: it is "stateless by default", `filter` enables partial clone, and `packfile-uris` and `server-option` allow out-of-band packs and custom options ([git protocol v2](https://git-scm.com/docs/protocol-v2)). Two things are unverified: whether go-git v6 is tagged stable, and whether its server path's dependency closure is free of `net`. The earlier report measured v5's `plumbing/*` and `storage/filesystem` as clean. v6 needs the same `go list -deps` check.

### Shred below git, per key on blocks, and tolerate missing objects

Git object IDs hash content, so erasing one object inside git means rewriting every descendant commit and running GC. Encrypting inside git does not help revocation. git-crypt has no "remove user" command, and a revoked user can still decrypt all old history ([git-crypt #47](https://github.com/AGWA/git-crypt/issues/47)). After a SOPS recipient is removed, "the old encrypted blobs remain decryptable in git history" ([Protea docs](https://protea.readthedocs.io/en/stable/appendix/secrets.html)). Shredding must sit *below* git, where blocks or packs are encrypted under keys the storage layer can destroy. That is the KBFS layering: objects are plaintext to the client, a custom storer encrypts blocks, and block IDs hash ciphertext ([KBFS crypto spec](https://book.keybase.io/docs/crypto/kbfs)).

That layering has a visible cost, which is an inference. Trees and commits that referenced a shredded blob keep their hashes, so clones see dangling references and must tolerate missing objects. Protocol v2's partial-clone semantics are the nearest standard mechanism ([git protocol v2](https://git-scm.com/docs/protocol-v2)). Trees and commit messages also carry filenames and intent, so the key unit has to cover the trees and commits written under it, or the shred leaks the metadata it was meant to remove. None of this has been tested.

For ParleyInn this matters less than it seems. Code stays on the user's git, and code pushed to GitHub is outside ParleyInn's custody whatever ParleyInn does. The layering matters for a git *view* of the record, and for any companion that wants to own encrypted code storage.

## A chat interface needs a verifiable log whose content can go

The chat half is about deletion semantics, not features. Every chat system with verifiable history keeps a tombstone or skeleton. Every chat system with real deletion gets it by keeping content out of verifiable history. Crypto-shredding is the one way to have both. The chat research found no surveyed chat product that documents it as a feature; Matrix redacts, Buzz deletes relay-side, and Fossil expires ([Matrix C-S API](https://spec.matrix.org/latest/client-server-api/#redactions); [Buzz ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md); [Fossil chat](https://fossil-scm.org/home/doc/trunk/www/chat.md)).

### Matrix keeps the graph valid through redaction, with one leak

Matrix is the only mature protocol that standardises a verifiable event graph with content removal. Redaction strips every key the protocol does not need, "cannot be undone", and allows "server owners to delete the offending content from the databases" ([Matrix C-S API: redactions](https://spec.matrix.org/latest/client-server-api/#redactions)). The trick is what gets hashed. "The event ID is the reference hash of the event", computed after "the event is put through the redaction algorithm", while a separate content hash "covers the complete event including the unredacted contents". Signature checks "should succeed whether we have been sent the full event or a redacted copy" ([Room v11](https://spec.matrix.org/latest/rooms/v11/); [Matrix S-S API](https://spec.matrix.org/latest/server-server-api/)). In practice it is softer: "some server implementations retain the redacted fields for a short time" ([Room v9](https://spec.matrix.org/v1.19/rooms/v9/)), and MSC4117 proposes reinstating redacted events ([MSC4117](https://git.sudo.is/matrix/matrix-doc/src/branch/travis/reinstated-events/proposals/4117-reinstating-events.md)).

The leak is the `hashes` key. Redaction keeps it, and it holds an unsalted SHA-256 over the full original event. Anyone holding a guess at short content, such as "yes", a file path or a known line of code, can confirm it against that hash. ParleyInn should borrow the reference-hash idea, but commit to ciphertext or to a keyed hash, so nothing is left to confirm a guess against once the key is gone. That is an inference from the spec text.

Matrix's Go story is thin. Synapse runs 80.1% of servers and Dendrite 2.0% ([TWIM 2026-04-07](https://matrix.org/blog/2026/04/07/this-week-in-matrix-2026-04-07/)), and Dendrite "is now maintained at element-hq/dendrite" because the Foundation "is unable to resource maintenance" ([matrix-org/dendrite](https://github.com/matrix-org/dendrite)). mautrix-go is a capable client and E2EE framework, but it is MPL-2.0 ([mautrix/go](https://github.com/mautrix/go)), off ParleyInn's allow-list. MLS for Matrix is still a proof of concept, because "MLS assumes that epochs...have a linear ordering" ([arewemlsyet](https://arewemlsyet.com/)).

### Nostr carries git events but deletes only on request

NIP-09 deletion is a request. "Relays SHOULD delete or stop publishing any referenced events", but "SHOULD continue to publish/share the deletion request events indefinitely", and deletion is not guaranteed "because it is impossible to delete events from all relays and clients" ([NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md)). NIP-44 v2, audited by Cure53 in December 2023, states "No forward secrecy: when a key is compromised, it is possible to decrypt all previous conversations" and "No post-quantum security" ([NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md)). NIP-17 gift-wraps each message under a fresh random key and randomises timestamps. Its forward secrecy is "optional", through disappearing messages, and otherwise messages are "Fully Recoverable... with the user's private key" ([NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md)). NIP-EE, MLS over Nostr, is superseded by the Marmot Protocol ([NIP-EE](https://github.com/nostr-protocol/nips/blob/master/EE.md)). An IACR paper presents practical attacks on Nostr; only its title was reviewed ([Kimura et al.](https://eprint.iacr.org/2025/1459.pdf)).

Nostr's useful contribution is NIP-34's link between conversation and code. A patch event carries `git format-patch` output and an `r` tag holding the repository's "earliest-unique-commit-id". That gives every repository a stable, host-independent identity a chat room can key on. Statuses (kinds 1630–1633) track open, applied, closed and draft ([NIP-34](https://github.com/nostr-protocol/nips/blob/master/34.md)). Nostr's cooperative deletion and static keys rule it out as the erasure layer. Shredding is only a guarantee if ParleyInn controls the only copy and the keys, which is an inference from NIP-09 and NIP-44.

### MLS suits a single authority, but Go has no audited implementation

RFC 9420 gives "efficient asynchronous group key establishment with forward secrecy (FS) and post-compromise security (PCS)" for groups from two to thousands, through a "largely untrusted" delivery service ([RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html)). Its deletion schedule is the key-deletion half of crypto-shredding. "As soon as a group member consumes a value, they MUST immediately delete (all representations of) that value" ([RFC 9420 text](https://www.rfc-editor.org/rfc/rfc9420.txt)). A single-authority ParleyInn store would satisfy MLS's linear-epoch assumption, which Matrix cannot.

MLS still fits ParleyInn badly, for three reasons. First, its forward secrecy is a *transport* property: the deletion schedule removes keys members hold ([RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.txt)). By inference, that conflicts with "Claude recalls exact history on demand" unless messages are re-encrypted at rest under a separate storage key. Second, ratchet clients must carry state, which disposable cloud sandboxes do not; the Element Web proof of concept "does not persist state" ([arewemlsyet](https://arewemlsyet.com/)). Third, the Go code is immature. `emersion/go-mls` is MIT with RFC test vectors, but "has not yet been audited for security issues" and has 32 stars ([emersion/go-mls](https://github.com/emersion/go-mls)). `BitravenS/go-mls` (June 2025) and `thomas-vilte/mls-go`, under Discord's dave-go, have no known audit ([BitravenS/go-mls](https://pkg.go.dev/github.com/BitravenS/go-mls); [dave-go](https://pkg.go.dev/github.com/thomas-vilte/dave-go)). The Signal Double Ratchet is the per-message alternative, where each message key can be deleted alone ([Signal Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)).

### XMPP, SimpleX and Signal agree that deletion is a request plus a tombstone

XEP-0424 Message Retraction, in Council Last Call until 20 July 2026, says a retraction "can only be considered an unenforceable request". Retractions must stay in the MAM archive so offline clients learn of them, tombstone-capable servers replace content with `<retracted/>`, and "there can never be a guarantee that a retracted message was never seen" ([XEP-0424](https://xmpp.org/extensions/xep-0424.html)). SimpleX requires receiving clients to soft-delete, replacing the message with "message is deleted" ([SimpleX protocol](https://simplex.chat/docs/protocol/simplex-chat.html)). Bluesky's spring 2026 roadmap makes non-public "permissioned data" a focus, but says nothing about DMs or end-to-end encryption ([AT Protocol roadmap](https://atproto.com/blog/2026-spring-roadmap)).

### Agent tools ship mailboxes, not protocols

What agent tools actually ship is simpler than any protocol. In Claude Code agent teams, still experimental, "each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`", and the team directory is removed at session end ([agent teams](https://code.claude.com/docs/en/agent-teams)). Cross-session messaging uses a per-session Unix socket on one machine, "never through Anthropic servers", and goes "through Anthropic servers" across machines. Messages are plain text, and `crossSessionInbound` takes accept, hold or refuse ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)). The trust model is the one I2 asks for: a message from another agent "never counts as your consent", and in auto mode a classifier reviews every inter-agent message before delivery ([agent teams](https://code.claude.com/docs/en/agent-teams)).

MCP Agent Mail keeps "human-readable markdown in a per-project Git repo" for every message, plus SQLite FTS5 ([mcp_agent_mail](https://github.com/Dicklesworthstone/mcp_agent_mail)); once pushed, that history cannot be erased (inference). Gas Town, a Go orchestrator for 20–30 Claude Code agents, routes mail to an agent, a queue or a channel ([Exploring Gas Town](https://embracingenigmas.substack.com/p/exploring-gas-town)). Its README mentions `gt mail check --inject` for runtimes without hooks ([gastown](https://github.com/steveyegge/gastown)). If that puts mail straight into context, it is the automatic path I2 forbids; this is inferred from the flag's name. Happy encrypts Claude Code and Codex sessions before they reach its relay ("Your code never leaves your devices unencrypted") but does not name its cipher ([slopus/happy](https://github.com/slopus/happy)). In Cursor's Slack Assistant pane, "every message spawns a new cloud agent, with no way to follow up on an existing one" ([Cursor forum](https://forum.cursor.com/t/slack-assistant-pane-every-message-spawns-a-new-cloud-agent-with-no-way-to-follow-up-on-an-existing-one/165947)). Delta and Buzz bind a thread to a session persistently, which is the stronger model.

## Crypto-shredding is a strong measure, not a recognised erasure

The technique is mature. The legal status is not. ParleyInn can build shredding with confidence, but it should describe it as a strong technical measure. It should not claim GDPR-compliant erasure.

### The EDPB will not equate key deletion with erasure

The EDPB adopted version 2.0 of its Guidelines 02/2025 on blockchain on 7 July 2026, after a consultation draft adopted on 8 April 2025 ([EDPB v2.0](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). The guidelines are about blockchains. Their reasoning applies by analogy to any immutable, hash-linked record that may be replicated, and ParleyInn's is one; that reading is an inference, not EDPB text. Five positions bear directly on ParleyInn, all from that PDF:

- **Encrypted data is personal data.** "Encrypted personal data is still personal data and encryption does not remove the need for GDPR compliance" (para 51). After key deletion, data stays unintelligible only "until the algorithm is broken... or if the key had already been compromised or leaked". "Even state-of-the-art encryption perfectly implemented will be overtaken by time if the blockchain is retained indefinitely" (para 51).
- **Impossibility is no excuse.** "Technical impossibility cannot be invoked to justify non-compliance with GDPR requirements" (para 50). Modifications "may not even impact all copies of the original block" (para 50).
- **Keep personal data off the ledger, even encrypted or hashed.** It is "not advisable to register personal data in those forms [clear text, encrypted or hashed] on a blockchain. Instead, personal data in those forms should be stored off-chain" (para 104). On-chain data should be "effectively rendered anonymous" on erasure, which presupposes that the off-chain data allowing indirect identification "is erased" (para 103). If retention is shorter than ledger life and no deletion or anonymisation technique exists, "no personal data should be stored on the chain" (paras 119–120).
- **Keyed hashes, commitments and tombstones are acceptable.** The EDPB lists three measures: encrypt payloads, store only a keyed hash or KDF output with data and key off-chain, or store a perfectly hiding commitment that once data and witness are deleted is "useless... neither possible to recover nor to recognise the original personal data" (paras 32–34, 51–54). Keyed or salted hashes become unlinkable after deletion only if "the keys have not been compromised or leaked, and the salt was not leaked or poorly chosen". Unsalted, unkeyed hashes are generally insufficient (para 52). An "anonymised transaction" can lose all meaning yet "still exists to allow the verification of integrity for other, remaining transactions" (para 64), which is the tombstone model.
- **Cryptography ages.** "All encryption systems have an undetermined, but limited, lifespan", including against "cryptanalytically-relevant quantum computers", so controllers need periodic reassessment and planned migration (para 96). Key management must be part of the risk assessment (para ~93), and content confidentiality alone does not protect metadata (para 65).

Industry consultation responses asked the EDPB to say that key destruction fulfils erasure. The adopted text does not use that wording ([Bitkom response](https://www.edpb.europa.eu/sites/default/files/webform/public_consultation_reply/en_ff_bitkom-zu-den-edsa-leitlinien_blockchain_datenschutz_juni-2025.pdf); [GBBC response](https://www.edpb.europa.eu/sites/default/files/webform/public_consultation_reply/gbbc-edpb-draft-guidelines-02_2025.pdf)).

### Courts and other regulators leave room for an argument

The CJEU's judgment in EDPS v SRB (C-413/23 P, 4 September 2025) confirmed a relative approach: pseudonymised data may be personal for a controller who can re-identify but not for a recipient who cannot ([Bird & Bird](https://cm.twobirds.com/en/insights/2025/eu-the-srb-decision-a-new-era-for-personal-data-and-data-processing-agreements); [Clifford Chance](https://www.cliffordchance.com/insights/resources/blogs/talking-tech/en/articles/2025/09/pseudonymized-data-after-edps-v-srb.html)). That strengthens the argument that ciphertext whose key is destroyed everywhere is no longer personal data. It is an argument, not a ruling on shredding. The UK ICO's older guidance, quoted by secondary sources, accepts data "put beyond use" when the controller will not use it, gives nobody access, secures it, and commits to deleting it when possible ([The Register](https://www.theregister.com/2018/05/31/backup_gdpr_analysis/)).

### Every technical precedent has the same shape

Mathias Verraes named the pattern in 2019: encrypt sensitive attributes "with a different encryption key for each resource (such as a customer)", and delete the key to erase, which "effectively makes all copies and backups of the sensitive data unusable". He warns that "today's unbreakable encryption could be tomorrow's infosec disaster", and that shredding does nothing for consumers that stored decrypted data ([Verraes, Crypto-Shredding](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)). His companion pattern, Forgettable Payloads, keeps the payload in a deletable store and only a reference in the event ([Verraes, Forgettable Payloads](https://verraes.net/2019/05/eventsourcing-patterns-forgettable-payloads/)). Kurrent, AxonIQ, Cratis and a Go package, `eskit/gdpr`, ship per-subject keys ([Kurrent](https://kurrent.io/blog/protecting-sensitive-data-in-event-sourced-systems-with-crypto-shredding-1); [AxonIQ](https://www.axoniq.io/blog/protect-sensitive-data-in-an-event-sourced-application); [Cratis](https://www.cratis.io/chronicle/compliance/key-lifecycle.md); [eskit/gdpr](https://pkg.go.dev/git.nullsoft.is/ash/eskit/gdpr)). Confluent wraps data keys under a KMS key but documents no erasure workflow ([Confluent CSFLE](https://docs.confluent.io/platform/current/security/protect-data/csfle/quick-start.html)).

Every precedent shares one shape. Per-subject or per-folder data keys are wrapped by a higher key, the ciphertext is kept, and deletion destroys the data key. Tamper evidence survives because the hash structure commits to ciphertext or to a redacted or keyed form, not to plaintext. Nobody re-encrypts history on rotation: KBFS says "don't bother to reencrypt old blocks", and Keybase teams rotate lazily ([KBFS crypto spec](https://book.keybase.io/docs/crypto/kbfs); [Keybase CLKR](https://book.keybase.io/docs/teams/clkr)). So revoking a device never removes what it already had. By inference, shredding granularity equals the lowest key level stored independently; a *derived* key cannot be shredded on its own.

C2SP tlog-tiles, the earlier report's format, is neutral: entries are "arbitrary" bytes, so the log commits to whatever ParleyInn puts in a leaf ([C2SP tlog-tiles](https://github.com/C2SP/C2SP/blob/main/tlog-tiles.md)). Redactable blockchains use chameleon hashes whose trapdoor lets a block be rewritten without breaking links ([Redactable Blockchains overview](https://arxiv.org/html/2508.08898v1)). The trapdoor weakens tamper evidence, so a security-first tool should not adopt them.

### Shredding fails through copies, derivatives and time

Shredding erases only what the key protected, and only if every copy of the key is gone. The EDPB names three failure modes: the replica problem (para 50), keys or salts that leaked (para 52), and ciphertext that outlives its algorithm (paras 51 and 96) ([EDPB v2.0](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). RFC 9420 makes "all representations" of a secret the deletion target, which counts in-memory copies ([RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.txt)). Verraes adds derived values ([Verraes](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)).

Four further risks are inferences without a primary source in the notes:

- **Process memory.** Go cannot reliably zeroise memory, because the GC copies values. Short-lived hook processes help.
- **Derived copies.** The model's context and provider-side logs are plaintext outside ParleyInn's control. Shredding cannot recall them.
- **Backups.** A keystore backup defeats shredding unless it is itself encrypted under a key destroyed on a schedule. That window is the effective erasure delay and should be documented.
- **Deterministic encryption.** SIV-style or convergent encryption leaks which plaintexts are equal. Records full of repeated content need randomised AEAD.

## A design for ParleyInn that keeps the invariants

The design extends the earlier report's record without changing its shape. Per-origin chains, tlog-tiles segments and signed checkpoints that bind their predecessor all stay. What changes is what a leaf commits to, where keys live, and how the git and chat views sit outside the core. There are three layers. The record and the keystore live inside the I4 binary. The views live outside it. Everything in this section is a synthesis of the sources above, so all of it is inference unless a citation says otherwise.

### The chain commits to keyed hashes of ciphertext envelopes

Each event becomes an envelope: a header plus ciphertext. The header holds origin, sequence number, previous-leaf hash, session ID, key ID and algorithm ID, kind, provenance and trust class, and a commitment to the ciphertext. The chain leaf hashes the header only. The ciphertext is XChaCha20-Poly1305 or AES-256-GCM under a per-event key derived as `HKDF(session_DEK, "parinn/event", seq)`, with the header as associated data. That binds ciphertext to its position, so it cannot be replayed elsewhere. The commitment is an HMAC of the ciphertext envelope under a commitment key that is derived from, or stored with, the session's data key and shredded with it. No header field is a plain hash of plaintext. This matches the KBFS habit of hashing ciphertext ([KBFS crypto spec](https://book.keybase.io/docs/crypto/kbfs)), Matrix's habit of hashing a form that survives removal ([Room v11](https://spec.matrix.org/latest/rooms/v11/)), and the EDPB's keyed-hash measure ([EDPB v2.0, paras 32–34 and 52](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)).

The keyed commitment has a cost, and it is an open choice. A plain SHA-256 of *randomised* ciphertext also leaks nothing to a guesser, who cannot produce the ciphertext without key and nonce, and it lets a keyless mirror verify payloads, as KBFS does. With the keyed form, a keyless mirror verifies only the chain and checkpoints. The keyed form is still the conservative default: para 104 lists hashed forms among those to keep off-chain, para 52 accepts keyed hashes, and only the keyed form is unlinkable *by construction* once the key is gone. A spike should decide whether keyless payload verification is worth the weaker legal position.

**Finding for the v1 SRS.** Today's purge leaves unsalted content hashes behind. REC-10 chains `SHA-256(prev_hash ‖ canonical_encoding(event))` with the payload hash included. REC-09 keys the payload store by SHA-256 of content. The `tombstones` projection in §8.2 keeps the "hash of removed content", and purge keeps each row's `hash` ([functional requirements](../../docs/srs/05-functional-requirements.md); [data and storage](../../docs/srs/08-data-and-storage.md)). After a purge, anyone holding the record can test a guess at short content, such as a name, a "yes" or a known path, directly against the payload and tombstone hashes, and against the row hash wherever the other canonical fields survive. Redaction before storage (SEC-08) removes known secret patterns, but not personal data in general. This is an inference from the SRS text, not a measured attack. It is the Matrix `hashes` leak, and the EDPB calls such hashes generally insufficient (para 52). The fix is to key the payload address and the tombstone hash under a per-session or per-store secret that purge destroys. The cost is that payload dedup becomes per-key. This is a change to the SRS and the gates that enforce it, so it needs the stakeholder's review, not a code pull request.

### Keys per session or subject, outside the record

The shred unit is a random **session data key**. Per-event keys are derived from it for nonce safety and are not stored. Where single-event redaction is needed, a per-event random key is wrapped by the session key instead, as KBFS does per block ([KBFS crypto spec](https://book.keybase.io/docs/crypto/kbfs)). Where a session holds a third party's personal data, a **subject key** follows Verraes' per-customer key ([Verraes](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/)). Content about that subject is encrypted under the subject's key, so one person's data can be shredded without destroying the session. How subjects are recognised at capture is unsolved.

Wrapped keys live in a mutable keystore under `$PARINN_HOME`, never in the record. If the record held the key, the hash chain would preserve exactly what shredding must destroy. Each data key is wrapped to every authorised device or host recipient, age-style ([age README](https://github.com/FiloSottile/age/blob/main/README.md)). A hybrid ML-KEM recipient answers part of the EDPB's quantum concern. A project key-encryption key optionally gives a second shred granularity. Revocation rotates forward, as Keybase's lazy rotation does ([Keybase CLKR](https://book.keybase.io/docs/teams/clkr)). A revoked device keeps what it had, and the only remedy is to shred the affected keys everywhere. Key loss is permanent lockout ([Anytype data erasure](https://doc.anytype.io/anytype/data/data-erasure-and-recovery.md)), so recovery (paper key, second device) has to be designed before the feature ships, not after. This all sits under SEC-09 (encryption at rest) and SEC-10, which already says credentials are resolved per use from an explicit secret reference ([security requirements](../../docs/srs/06-security.md)).

### Shredding destroys the key, deletes the ciphertext, and leaves a signed tombstone

A shred has six steps, in this order:

1. Check for a legal hold on the scope. A hold refuses the shred, and the refusal is audited.
2. Destroy every wrapped copy of the data key (or subject key) on every keystore replica.
3. Delete the ciphertext from the payload store wherever ParleyInn has custody, using the existing purge machinery: SQLite `secure_delete`, a rewrite and unlinked payload files (SEC-14, [security requirements](../../docs/srs/06-security.md)).
4. Append a signed `KeyDestroyed{key_id, scope, reason, actor}` leaf to the record.
5. Rebuild every projection that held plaintext, including FTS, landmarks and pins, deterministically from the record.
6. From then on, recall of the range returns a tombstone notice, as RCL-06 already requires for purges ([functional requirements](../../docs/srs/05-functional-requirements.md)).

Deleting the ciphertext as well as the key is what moves ParleyInn from "unintelligible" toward the EDPB's "stored off-chain and erased" (paras 103–104). The key-only step remains the guarantee for copies ParleyInn cannot reach. The tombstone is the EDPB's anonymised transaction (para 64) and Recital 66's "traceability" ([EDPB v2.0](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). It follows the "log the deletion as an event" pattern of Nostr kind 5, XMPP retraction and Buzz's `EventDeleted` ([NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md); [XEP-0424](https://xmpp.org/extensions/xep-0424.html); [ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)). Unlike Buzz's fire-and-forget audit, a shred whose tombstone cannot be written must fail loudly and leave the key in place.

The invariants already have room for this. I1 lets an operator purge explicitly, provided the purge is recorded. I5 quarantine stays the reversible step, and shredding is the irreversible one. The chain keeps verifying, because it never committed to plaintext. Documentation should state the backup window and the crypto-agility plan. It should call the feature crypto-shredding, not GDPR erasure.

### Git and chat are separate opt-in processes

**The git view.** A `git-remote-parinn` helper would let `git clone parinn::<scope>` browse the record as git: sessions as read-only repositories or refs, linked to commits from evidence the record already holds. It would use go-git v6 plumbing over a custom storer that reads the projection and serves `UploadPack` over stdio ([go-git v6 transport](https://pkg.go.dev/github.com/go-git/go-git/v6/plumbing/transport)). A stdio helper opens no socket and could arguably live inside I4. It should still be a separate binary: that keeps go-git out of the core's dependency budget and the git attack surface out of the hook path, and only those who want it install it. A smart-HTTP or SSH git *server* is network code and belongs with the earlier report's relay, built and reviewed separately. ParleyInn does not host code. A companion owning encrypted code storage would be Keybase-shaped, with the log as truth, packs encrypted per key below git and clients that tolerate missing objects. That is a different product.

**The chat view.** A separate process renders the record as rooms and threads and accepts human messages. Rooms key on the repository's earliest unique commit, like NIP-34's `r` tag ([NIP-34](https://github.com/nostr-protocol/nips/blob/master/34.md)), plus the branch, like Buzz's branch-as-room ([block/buzz](https://github.com/block/buzz)). Each session is a thread, in the manner of Zulip topics ([Zulip topics](https://zulip.com/help/introduction-to-topics)). Messages enter through the core's ordinary ingest, marked untrusted by capture path, never by content, and encrypted under the session key. They reach a model only through pull-only, enveloped recall, never through a restore block or an `--inject`-style push. That is Claude Code's "never counts as your consent" rule made structural ([agent teams](https://code.claude.com/docs/en/agent-teams)). Local delivery can use a Unix socket owned by the view, as Claude Code's cross-session messaging does ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)); cross-machine delivery goes through the relay. Live chat that should never become record can use Fossil's unsynced, expiring side table ([Fossil chat](https://fossil-scm.org/home/doc/trunk/www/chat.md)). If MLS is ever used, it protects live delivery only.

### Copies that leave custody cannot be shredded

Some copies are out of reach by construction. A bridge to Matrix, Nostr or Slack delivers copies to servers ParleyInn does not control. NIP-09 and XEP-0424 both admit that deletion cannot follow them, and the EDPB's replica point says the same ([NIP-09](https://github.com/nostr-protocol/nips/blob/master/09.md); [XEP-0424](https://xmpp.org/extensions/xep-0424.html); [EDPB v2.0, para 50](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). The same holds for recalled content sent to the model provider, git objects pushed to a forge, and anything a human copied out of the chat view. ParleyInn's shred guarantee should therefore be scoped in writing to the custody it controls. Bridges should be opt-in projections that carry no keys. Each egress of plaintext should be an audited event, so an operator can see which shredded scopes had already left (I6).

## Risks and open questions

### Risks

- **Legal.** Regulators do not recognise key deletion alone as erasure, and the EDPB discourages even encrypted or hashed personal data in an immutable log ([EDPB v2.0, paras 51 and 104](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). Deleting ciphertext alongside the key narrows the gap but does not close it for copies ParleyInn cannot reach.
- **Metadata stays in the clear.** Headers keep session IDs, kinds, sequence numbers and timing so the chain can verify. That metadata is itself sensitive, as the EDPB's para 65 and Keybase's visible team membership both show ([Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone)).
- **Key loss.** User-held keys mean unrecoverable data when the key is lost ([Anytype data erasure](https://doc.anytype.io/anytype/data/data-erasure-and-recovery.md)), and I9 forbids degrading the agent when the keystore is unavailable. When it is, ParleyInn must either skip capture, which I1 resists, or encrypt to a standing recovery recipient, which widens who can read. Which one keeps I1, I8 and I9 together is undecided.
- **Ciphertext lifetime.** A record meant to last indefinitely will outlive its algorithms ([EDPB v2.0, para 96](https://www.edpb.europa.eu/system/files/2026-07/edpb_guidelines_202502_blockchain_v2_en.pdf)). Algorithm IDs in key IDs and ciphertext deletion are the mitigations.
- **Scope creep.** Building a forge, a chat server or an MLS stack would pull network code, heavy dependencies and off-allow-list licences (GPL-3.0 gcrypt, MPL-2.0 mautrix-go, AGPL Peergos and SimpleX) toward the core. Buzz shows what a real chat-and-git server costs to run: Postgres, Redis and object storage ([block/buzz](https://github.com/block/buzz)).
- **Single steward.** Keybase's freeze is the warning for any system that puts identity and keys under one company ([Decrypt](https://decrypt.co/28121/keybase-users-revolt-following-zoom-acquisition)). ParleyInn's local-first, no-network design avoids that by construction. It also has no hosted recovery path.

### What to verify or spike next

1. **Raise the purge-hash finding with the stakeholder.** REC-09, REC-10 and the §8.2 tombstone projection keep unsalted SHA-256 of content after purge. Decide whether to key them, and what that does to payload dedup. This touches the SRS, so it goes through stakeholder review.
2. **Measure go-git v6's server path.** Run `go list -deps` on `UploadPack` and `ReceivePack` with a custom storer against the import-closure test, and confirm whether v6 is tagged stable ([go-git v6 transport](https://pkg.go.dev/github.com/go-git/go-git/v6/plumbing/transport)).
3. **Choose the commitment.** Compare a keyed HMAC with a plain SHA-256 of randomised ciphertext, weighing keyless-mirror verification against the EDPB's keyed-hash language. Record the decision in an ADR.
4. **Spike shredding under git.** Serve a repository whose blobs are encrypted per key, shred one key, and observe stock git clone, fetch and fsck behaviour with partial-clone filters. Confirm that repacking never mixes shredded and live keys.
5. **Spike the keystore.** Build a file keystore under `$PARINN_HOME` with a passphrase or age identity. Verify that age core has no `os/exec` outside plugins and whether godbus pulls in `net`. Evaluate go-tpm as an optional root. Write down the backup window.
6. **Get a legal reading.** Ask counsel for an opinion on EDPB v2.0 applied to this design. Fetch the AEPD technical note, GDPR Art. 17(3), the EDPB's pseudonymisation guidelines (01/2025) and the ICO's primary text, and decide how legal holds block shredding.
7. **Prototype the chat view locally.** Use a Unix socket, rooms keyed by root commit and branch, every inbound message enveloped as untrusted, and recall-only exposure. Test it against SEC-13's recall-taint flag.
8. **Close the Buzz questions before any bridge.** Find out whether a kind 5 deletion hard-deletes the Postgres row and its search vector, and whether `EventDeleted` audit entries hold content or a hash ([ARCHITECTURE.md](https://github.com/block/buzz/blob/main/ARCHITECTURE.md)).
9. **Fill the protocol gaps.** Check Go Nostr libraries, the Marmot protocol, Megolm's exact properties and any audit of a Go MLS library.
10. **Watch the closed products.** Track whether Zed Delta publishes its licence, encryption and erasure model, and whether Entire's network ships encryption when it opens up ([Delta public beta](https://zed.dev/blog/delta-public-beta); [Entire blog](https://entire.io/blog/an-entirely-new-git-hosting-network)).
11. **Research proofs of deletion.** Key destruction cannot be proven to a third party without trusted hardware. Research TPM- and HSM-attested destruction before any compliance claim.

## Conclusion

The stakeholder's angle holds up in parts. Owning storage is right, and already the direction. Owning keys is the new, valuable piece: per-session and per-subject data keys turn "payloads hashed apart from the chain" into real erasure for everything in ParleyInn's custody, and make shared segments safe to carry as ciphertext. Owning the network is not ParleyInn's job; I4 forbids it, and Buzz shows the operating cost. A git interface is well supported, but for ParleyInn it is a read-only view, not a forge. A chat interface is a projection whose human input is untrusted by construction. Matrix contributes the hashing idea and its one mistake, and Claude Code the trust rule. Both interfaces belong in separate, opt-in processes.

Crypto-shredding is the strongest available tool, not a legal safe harbour. The EDPB's July 2026 guidance says how to build it: keyed hashes instead of plain ones, ciphertext deleted with the key, a signed tombstone, and an honest statement that copies outside custody cannot be erased. Built that way, ParleyInn would hold the quadrant no one holds today: code linked to conversation, verifiable history, and content that can truly go. The first step costs nothing now. Stop leaving unsalted content hashes behind when content is purged.
