# Own the record; let git carry copies

ParleyInn should keep agent session history in its own append-only store. It should not use git, a git forge or a git alternative as that store. Git should be one optional, one-way carrier for sealed, signed segments, alongside a separate real-time relay and plain file sync. None of these carriers runs inside the shipped binary. Version control itself does not need to leave git, at least for code. Every serious agent-era challenger keeps git at the edge: Cursor Origin, Zed Delta, GitLab's next-gen SCM, Entire, jj and ERSC. The historic departures were driven by monorepo size and read load years before agents arrived (Google, Meta, Microsoft, the package managers, Hugging Face). The strain agents cause today falls on hosts: GitHub had to plan for 30 times its scale. What has moved off git is the session record. GitHub, Anthropic, Cursor, Hugging Face, Beads, Gas Town, GitButler, Letta and MCP Agent Mail all keep transcripts out of git, or took them out, and none of the roughly 175 systems surveyed moved raw history into git. Hacker News agrees on the shape. It wants the lossless record kept, private by default, redacted, linked to commits by an ID, and out of the main history. The design has four parts: per-origin hash-chained segments in a transparency-log format, signed checkpoints that bind their predecessor, import treated as untrusted and reached only through enveloped pull-only recall, and payloads hashed apart from the chain so they can be erased. This fits all seven invariants. It also gives the stakeholder real-time sharing across worktrees, machines, sandboxes and open-source projects. The main open risks are unmeasured: whether sandbox git proxies accept custom refs, and whether crypto-shredding satisfies erasure law.

## Agents strain git hosts, not git's data model

The question "should version control move off git?" has two answers. For code, no. For everything git was never built to hold, it already has. The evidence separates three layers: the snapshot model and wire protocol, the server storage behind a forge, and the record of how code came to be written. Only the third is new, and only the second is breaking under agent load.

### The big departures predate agents and were about scale and reads

Google never put its monorepo in git. It ran one Perforce instance for over a decade, then built Piper on Bigtable and later Spanner. By 2016 it held 86 TB and two billion lines, and automation made **24,000 commits a day against 16,000 human changes** ([Wikipedia: Piper, citing Potvin & Levenberg](https://en.wikipedia.org/wiki/Piper_(source_control_system))). The paper's summary says git "would require splitting into thousands of repos" ([AcaWiki](https://acawiki.org/Why_Google_Stores_Billions_of_Lines_of_Code_in_a_Single_Repository)). Machines outwriting humans is therefore a solved workload, but it was solved by a central, linearised, database-backed log with admission control. Rosie shards large changes, caps outstanding shards and runs at low priority ([SWE book ch. 22](https://abseil.io/resources/swe-book/html/ch22.html)). Meta rejected git in 2014 because "Git examines every file and naturally becomes slower and slower as the number of files increases" ([Meta Engineering](https://engineering.fb.com/2014/01/07/core-infra/scaling-mercurial-at-facebook/)). Meta moved through Mercurial to Sapling, Mononoke and EdenFS, and says public systems "were not, and still are not, capable" of its repository size ([Meta: Sapling](https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/)).

Microsoft is the counterexample that stayed. Windows moved to a git repository of about 300 GB and 3.5 million files, with 8,421 pushes a day. That needed a virtual filesystem, a custom server protocol and a git fork ([Brian Harry](https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/)). The work was then upstreamed as Scalar in Git 2.38 ([GitHub Blog](https://github.blog/open-source/git/the-story-of-scalar/)). The package managers left git *as a database*, not git as version control. Cargo's git index clone was 215 MiB against a 16 MiB tarball, and the sparse HTTP protocol cut resolution from 2–4 minutes to under 10 seconds ([Cargo team](https://hackmd.io/@rust-cargo-team/rkm1ttkns)). Homebrew 4.0 replaced git-cloned taps with JSON and cut auto-update from every 5 minutes to every 24 hours ([Homebrew](https://brew.sh/2023/02/16/homebrew-4.0.0/)). CocoaPods moved to a CDN ([CocoaPods](https://blog.cocoapods.org/CocoaPods-1.8.0-beta/)). Go went straight to a module proxy plus a checksum database, an append-only Merkle log with signed tree heads and tiles ([Go Blog](https://go.dev/blog/module-mirror-launch)). Hugging Face kept git refs as the user model but moved **77 PB across more than 6 million repositories** from LFS to Xet's content-defined chunks on S3 ([HF Blog](https://huggingface.co/blog/huggingface-hub-v1)). It also ran ParleyInn's exact workload, raw Claude Code JSONL synced from many machines. Its docs say a git repository "is not meant to work as a database with a lot of writes", that the experience degrades after a few thousand commits, and that live traces should be batched at least 5 minutes apart ([HF Agent Traces](https://huggingface.co/docs/hub/en/agent-traces)).

### Agent load is breaking hosts, and hosts are rebuilding storage behind git

GitHub's CTO wrote in April 2026 that agentic workflows "accelerated sharply" from late December 2025. GitHub raised its capacity target from 10x to **30x**, with peaks of 1.4 billion commits and 90 million merged pull requests a month. The subsystems that buckled were git storage, MySQL, Actions, search and webhooks ([GitHub Blog](https://github.blog/news-insights/company-news/an-update-on-github-availability/)). An unofficial tracker measured GitHub's 90-day uptime at 87.26% ([The Register](https://www.theregister.com/software/2026/06/12/github-outages-persist-as-ai-coding-drives-traffic-surge/5255125)). Most of that list is derived indexes, not git's object format.

The response has been to rebuild storage behind git's wire protocol. Cursor's Continuity engine, which backs the Origin forge, stores each accepted push as an immutable packfile object in S3. A single index object is updated by compare-and-swap, and on-disk repositories are "a warm cache". Cursor reports up to 120 pushes a second on S3 Standard and over 300 on S3 Express One Zone, limited by git compaction ([Cursor](https://cursor.com/blog/git-at-any-scale)). GitLab's next-gen SCM keeps git compatibility but serves agents through server-side read and write APIs. It names a "clone tax" of 5–10 GB and 30+ seconds per agent invocation ([GitLab](https://about.gitlab.com/blog/gitlab-next-gen-scm/)). ERSC, now home to jj's creator, targets "thousands of commits per second" on a jj-based host that stays git-compatible, and is in early trials ([ERSC](https://ersc.io/blog/ersc-availability)). These are all server-side rewrites. None asks developers or agents to stop speaking git.

Two smaller notes on names. "Lore" also names tt-a1i/lore, a session-to-commit linker. It shows that the patch and `git commit` output already inside a Claude Code transcript are enough to attribute commits after squash or rebase, with no trailer ([tt-a1i/lore](https://github.com/tt-a1i/lore)). And Oak's newline-joined hash preimage caused three integrity bugs in six months: a filename with `\n`, a mutable hashed branch name, and Postgres timestamp truncation ([Oak](https://oak.space)). ParleyInn's RFC 8785 canonical encoding already guards against this class. Go's `encoding/json` breaks it by default, though, because it HTML-escapes `<`, `>` and `&` ([in-toto PR #588](https://github.com/in-toto/attestation/pull/588)).

Adoption friction is real even for git-compatible tools. Gradle evaluated jj and stayed on git because jj ignores `.gitattributes`, which caused a "persistent phantom modification" on `gradlew.bat` ([Gradle blog](https://blog.gradle.org/the-petty-reason-we-didnt-end-up-using-jj-at-gradle)). A jj user on Hacker News reports that "Claude forgets to use it all the time" ([HN](https://news.ycombinator.com/item?id=48631726)). The training-data argument is strong for any tool the agent must drive. It does not apply to a passive record the agent never touches, and that is exactly where ParleyInn sits.

## Every system that ran agent history at scale moved it out of git

The second half of the question is where agent session history should live. On this, the field has voted with its migrations. Of about 175 systems catalogued, not one moved raw history *toward* git. Projects that tried git as the store moved off it: MCP Agent Mail ended with SQLite as its source of truth, ByteRover dropped git within months, GitButler deleted prompt-in-commit, and Task Master moved its high-churn data out of the tree ([Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail); [ByteRover](https://github.com/campfirein/byterover-cli); [GitButler](https://blog.gitbutler.com/parallel-claude-code); [Task Master](https://github.com/eyaltoledano/claude-task-master)). The vendors that own both git and an agent keep only a pointer in git. GitHub's Copilot cloud agent puts an `Agent-Logs-Url` trailer on commits and keeps the log on GitHub's servers ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Claude Code cloud sessions use a `Claude-Session` trailer pointing at claude.ai ([Claude Code docs](https://code.claude.com/docs/en/claude-code-on-the-web)). Cursor's cloud agents keep transcripts encrypted under per-agent keys in Cursor's backend ([Cursor](https://cursor.com/docs/cloud-agent)).

### Beads, Gas Town and Buzz put a database in the hot path

Beads is the clearest migration story. From October 2025 to February 2026, its source of truth was a git-tracked `.beads/issues.jsonl`, kept in step with a SQLite cache by a 5-second debounced export, a custom field-level merge driver and 30-day tombstones ([v0.47.0 architecture](https://github.com/steveyegge/beads/blob/v0.47.0/docs/ARCHITECTURE.md)). Releases v0.50 and v0.51 deleted the daemon (~19,700 lines), the JSONL sync layer (~7,600 lines), the merge engine and the tombstones. Dolt became the sole store at v1.0.0 in April 2026 ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). Steve Yegge summed up the old design as "bidirectional sync, 3-way merge, two sources of truth, race conditions, and tombstone hell" ([Yegge, mirror](https://drss.io/feed/npub1na2ppcvpx7m7dg4d2rqelpq4xdj9z40cxu3avh4qcdq8dtupdcmqahmfge/gas-town-from-clown-show-to-v10)). Beads still uses the git remote, but only as a wire: Dolt history rides under `refs/dolt/data`, away from code branches ([sync concepts](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)). The Dolt era had its own failures. One commit per write grew to "gigabytes of storage for a few thousand beads", and the fix forces every other clone to re-clone ([history-squash](https://github.com/gastownhall/beads/blob/main/docs/recovery/history-squash.md)). In the 2026-08-11 data-loss incident, `bd init --force` silently recreated a missing database as empty ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). The lesson for ParleyInn is precise. These failures came from mutable rows reconciled across replicas. An append-only record that is never edited in two places avoids that class by construction. Beads also injects stored memories straight into sessions through `bd prime`, with no envelope ([remember.md](https://github.com/gastownhall/beads/blob/main/docs/cli-reference/remember.md)). That is the path I2 forbids.

Gas Town shows the architecture that results. All agents in a town write to **one Dolt SQL server, in transactions on `main`**. Git holds code worktrees, plus a "Ledger" plane that exports scrubbed, append-only JSONL to GitHub every 15 minutes ([dolt-storage](https://github.com/gastownhall/gastown/blob/main/docs/design/dolt-storage.md)). Its persistent mail costs a Dolt commit per message: "4 agents x 15 patrol cycles x 2 mails per cycle = 120 commits just for routine chatter" ([mail protocol](https://github.com/gastownhall/gastown/blob/main/docs/design/mail-protocol.md)). Gas Town also has exactly the gap ParleyInn targets. It stores no session record. It scrapes `~/.claude/projects/*.jsonl`, and its own audit admits that "no single ID connects" transcript, cost, event and bead, and that 17 of 28 touch points depend on Claude Code internals ([agent-api-inventory](https://github.com/gastownhall/gastown/blob/main/docs/design/agent-api-inventory.md)).

Block's Buzz, announced 21 July 2026, is the only credible match for "Buzz" in this space, and the stakeholder should confirm it is the project meant. It is "a Nostr relay: every message, reaction, workflow step, review approval, and git event is a signed event in one log". That log lives in **Postgres with full-text search**, with Redis for pub/sub and git served by the relay over NIP-34 and smart HTTP ([block/buzz](https://github.com/block/buzz)). Every agent has its own keypair plus a second signature binding it to its human owner ([SiliconANGLE](https://siliconangle.com/2026/07/21/block-launches-buzz-open-source-workspace-humans-ai-agents/)). Signatures do not encrypt, and committed events are searchable by the workspace ([flaviocopes](https://flaviocopes.com/buzz/)). Whether Buzz stores full transcripts or only what agents post is unverified. For ParleyInn, Buzz is a reference for signed append-only events and per-agent identity. It is not a case of git as storage.

### Entire's source shows what git-native transcripts cost

Entire is the most-funded git-native session store: a $60M seed, a Go CLI under MIT. Its source at commit `89c2616` (2026-10-01) confirms the design and exposes its limits. The CLI has two backends. The legacy one appends every checkpoint as a commit on one branch, `entire/checkpoints/v1`, so all agents and worktrees contend on one tip. The newer `git-refs` backend writes **one ref per checkpoint** at `refs/entire/checkpoints/<shard>/<id>`, sharded by the last two characters of a ULID ([refs_naming.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/checkpoint/refs_naming.go)). New setups have written it without asking since 0.10.0 ([setup.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/setup.go)). Entire's blog gives the reason: multiple agents could not "save their work at the same time without competing to update a shared branch" ([Entire blog](https://entire.io/blog/introducing-ref-based-checkpoint-storage)). Objects are built with go-git. Refs move through the git binary's `update-ref --stdin` with a compare-and-swap ([ref_cas.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/gitrepo/ref_cas.go)). Pushes ride the user's `git push` through a pre-push hook that drains a flock-protected queue, and they never force ([pushqueue.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/checkpoint/pushqueue.go)). This is a sound transport shape that ParleyInn can learn from.

The weaknesses matter more for a security-first product. Redaction fails closed for JSONL when a scanner degrades. It skips images, keys ending in `id` or `signature`, and path fields, though. Shadow-branch code snapshots stay unredacted in local git objects, and so does a worktree copy of the full transcript ([redact.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/redact/redact.go)). There is **no hash chain or signature over checkpoint content beyond git's object graph**. Signing is best effort, and nothing verifies signatures on read ([persistent.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/checkpoint/persistent.go)). There is no retention or GC. The binary imports `net/http` in 44 files and `os/exec` in 96, and PostHog telemetry is on by default ([telemetry](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/telemetry/detached.go)).

Most instructive is the 0.11.0 incident. A stale committed `checkpoint_remote` named a different owner. Entire logged "ignoring checkpoint_remote that appears to belong to another owner; pushing checkpoints to the push remote instead" and pushed transcripts to a **public** origin ([emotely#199](https://github.com/trost-systems/emotely/issues/199)). The source shows `PushURL` silently falling back to the origin URL in five cases, each with only a warning in a log file ([util.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/checkpoint/remote/util.go)). The follow-up, PR #2521, was merged on 2026-09-30 and is in no stable release. It prints a warning *after* delivery, and its commit message says "It blocks nothing" ([checkpoint_remote_hint.go](https://github.com/entireio/cli/blob/89c26160877a27a5017dc0bd614768c463e793bd/cmd/entire/cli/strategy/checkpoint_remote_hint.go)). In the incident's exact case, a different owner, pre-push still writes only the log warning and pushes to origin. Entire's own design choice puts availability over confidentiality. ParleyInn's I6 and I8 require the reverse.

The shapes are working-tree files, git notes, off-branch custom refs, and a database or content-addressed store with git at the edge. Git notes and shared mutable refs account for nearly all documented silent data loss. In gitwhy's test, 30 concurrent `git notes add` calls all exited 0, yet only 2–5 notes survived ([gitwhy](https://github.com/surajsrivastav/gitwhy)). memento's `git push refs/notes/*` published supposedly private full-audit transcripts ([memento](https://github.com/mandel-macaque/memento)). agentdiff retries a compare-and-swap without recomputing content, and its custom-ref store escapes branch protection ([agentdiff](https://github.com/codeprakhar25/agentdiff)). The systems that move multi-writer history safely all give each writer its own append-only lane and merge only when reading: Rekal's per-writer refs of framed segments, agentsview's per-origin journal of SHA-256-named segments, and Memorix's `events/<ns>/<device>/<seq>.jsonl` ([Rekal](https://github.com/rekal-dev/rekal-cli); [agentsview](https://github.com/kenn-io/agentsview); [Memorix](https://github.com/AVIDS2/memorix)). NTM learned that the writer must be the process, not the session. Its shared per-session hash chain forked as soon as two processes appended ([NTM](https://github.com/Dicklesworthstone/ntm)).

No surveyed tool combines full verbatim transcripts, many writers, a tamper-evident append-only record and treating recalled content as untrusted. Entire comes closest on the first two, and Buzz on signed events. The fourth is almost absent everywhere. Hermes wraps live tool output as untrusted but returns the same stored text unwrapped through `session_search` ([Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)). Engram's SessionStart hook pipes imported segments into context with no envelope ([Engram](https://github.com/Gentleman-Programming/engram)). LangGraph had four CVEs from rebuilding typed objects out of stored bytes ([LangGraph](https://docs.langchain.com/oss/python/langgraph/persistence)). That combination is ParleyInn's niche.

## Hacker News wants the record kept, private, and out of the main history

The debate has filled about a dozen large threads since early 2026. The central ones are "If AI writes code, should the session be part of the commit?" (497 points, ~391 comments) ([HN 47212355](https://news.ycombinator.com/item?id=47212355)), Entire's launch (611 points, 577 comments) ([HN 46961345](https://news.ycombinator.com/item?id=46961345)), the Claude Code session-URL default (209 points) ([HN 49498201](https://news.ycombinator.com/item?id=49498201)), DeltaDB (529 points) ([HN 49187256](https://news.ycombinator.com/item?id=49187256)), Cursor Origin (597 points, 454 comments) ([HN 49334209](https://news.ycombinator.com/item?id=49334209)), Buzz (378 points) ([HN 48995213](https://news.ycombinator.com/item?id=48995213)), and the "git for agents" Show HNs, Oak (216) and re_gent (129) ([HN 48631726](https://news.ycombinator.com/item?id=48631726); [HN 48063548](https://news.ycombinator.com/item?id=48063548)).

The consensus has four parts. First, do not put raw transcripts into the main history or pull requests. The top comment in the session-in-commit thread (53 replies) says sessions are full of "noise, incorrect implementations, and red herrings" ([HN](https://news.ycombinator.com/item?id=47214007)). Another commenter says committing them would spoil "study git commits to ground yourself" for future agents because "Context window is precious" ([HN](https://news.ycombinator.com/item?id=47230488)). Second, commit distilled intent: plan and spec files, ADRs, good commit messages ([HN](https://news.ycombinator.com/item?id=47214629)). Third, if full sessions are kept, keep them out of band, linked by ID, private and redacted. One developer calls his session-ID-per-commit script "a lifesaver when you are trying to debug an old commit" ([HN](https://news.ycombinator.com/item?id=49498363)). Another runs three repositories per project, with transcripts in a "Sensitive data" repo only a special agent can read ([HN](https://news.ycombinator.com/item?id=49505920)). Fourth, be sceptical of new VCSs "for agents". "Models know git because there's a monstrous amount of git in their training data" ([HN](https://news.ycombinator.com/item?id=48635235)), and "the performance of git isn't a bottleneck for agents" ([HN](https://news.ycombinator.com/item?id=48633789)).

The dissents are just as useful to ParleyInn. Provenance advocates say the session is the real source, and some treat linkage as professional attribution. dang wrote that "the prompts are the real source, while the GH repo or generated artifact is actually the object code" ([HN](https://news.ycombinator.com/item?id=47096202)). Another commenter: "We use flight data recorders on airplanes, though" ([HN](https://news.ycombinator.com/item?id=47213441)). A privacy and surveillance camp objects to hosted capture. The top DeltaDB comment (87 replies) reads "The code I write between commits is my thinking… I don't want my thoughts to be serialized, version controlled and publicly accessible" ([HN](https://news.ycombinator.com/item?id=48494076)). On Delta, removing uploaded conversations takes an email to Zed's privacy contact ([HN](https://news.ycombinator.com/item?id=49758135)). Vendor URLs draw distrust: "Do any of us truly believe these links will work 30 years from now?… Git is supposed to be the durable storage medium" ([HN](https://news.ycombinator.com/item?id=49499194)). The Origin thread was dominated by refusals to host code under SpaceX/xAI ownership and by calls for Forgejo, Radicle or Tangled instead ([HN](https://news.ycombinator.com/item?id=49348841)). Its storage thread praised the WAL design and called it "event sourcing at its finest". One critic objected that "S3 is a proprietary product, not an algorithm" ([HN 49348141](https://news.ycombinator.com/item?id=49348141)).

Three gaps in the HN record matter for positioning. Prompt injection through stored history is almost never raised. Memory poisoning is: "once there is one poisoned line of text it negatively affects everything else downstream" ([HN](https://news.ycombinator.com/item?id=49509345)). ParleyInn's I2 is ahead of the community and needs explaining as the fix for that complaint. Second, several people built "Claude JSONL into git notes" tools and abandoned them. cnotes' author "ended up not getting much out of it" ([HN](https://news.ycombinator.com/item?id=46962431)). Capture is easy; retrieval, redaction and a shared format are the unsolved parts. Third, HN readers are self-selected sceptics, and some threads drew astroturfing accusations, so vote-weighted consensus is a sentiment signal, not a measurement ([HN](https://news.ycombinator.com/item?id=49499267)). Taken together, the record favours a vendor-neutral, network-free, self-contained record with an open export format. That is what I4 and I10 already give ParleyInn.

## Git, alternatives and an own store, scored against ParleyInn's invariants

ParleyInn's SRS already makes its own store the record. Each project keeps an `events` table with a gap-free `seq`, a `prev_hash`/`hash` chain over RFC 8785 canonical JSON with SHA-256, and a content-addressed payload store keyed by SHA-256. Purge removes content but keeps the hashes, so the chain still verifies (SRS §8.1–8.3, REC-09). Multi-host shared stores are explicitly a v1 non-goal (NG4), and their design is deferred to OQ-07. So the real question is not what replaces the store. It is how the store becomes shareable without breaking an invariant. The table scores four candidate designs.

Git still earns a place. It is the one carrier every developer, sandbox and open-source project already has. Its sharp edges are known and can be designed around. GitHub enforces 100 MB per object and 2 GB per push. It recommends staying under 10 GB on disk, 5,000 branches, 3,000 entries per directory and **6 pushes a minute per repository** ([GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). At 2 KB per event, five million events come to about 10 GB before compression, so one busy team record reaches GitHub's guidance within months. Records must therefore travel as sealed segments of about a megabyte, spread across repositories by tenant. With 20 agents sharing one repository, each could push only every 3–4 minutes. GitHub's webhooks must answer within 10 seconds and failed deliveries are not retried ([GitHub Docs](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)). Git is a durability carrier, not a real-time one. Erasure is the other hard edge. Removing pushed data needs a Support ticket and survives in forks and clones ([GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). whogitit's "retention delete" left every deleted prompt in the notes history on every remote ([whogitit](https://crates.io/crates/whogitit)). Plaintext segments on a shared forge can never be redacted.

A plain forge cannot enforce one writer per ref either. Any token with push access can rewrite or delete another writer's ref. A forge can fork a log without anyone noticing, as gittuf documents ([gittuf](https://github.com/gittuf/gittuf)). Code.Storage sells exactly the missing server rules, compare-and-swap and one writer per ref ([Code.Storage](https://code.storage)). Tangled's Knot 2 refuses client pushes and deletes under `refs/cobs/*` ([Tangled](https://tangled.org)). Without such a host, integrity must come from ParleyInn's own signatures and witnesses, not from the forge. Forgejo is a good self-hosted remote for open-source projects that want independence from GitHub, but it changes the caps, not the model. Its own collaboration data lives in SQL, not git, and its federation has shipped only stars ([NLnet](https://nlnet.nl/project/Federated-Forgejo/)).

## Build an own record whose sealed segments any carrier can move

The recommendation has one core and three optional carriers. The core stays inside I4. It writes per-origin, hash-chained, signed segments into a local outbox and imports verified segments from an inbox. The carriers sit outside the shipped binary and move those files. They are the user's own git, a separately built and reviewed relay, and plain file sync. A carrier never defines truth. It only moves bytes the core can verify.

### The record and the segment format

Make every writer a single-writer origin, named by the hash of its public key and not by hostname. gitmem's `devices/$HOSTNAME` branches clobbered each other's history ([gitmem](https://github.com/panosAthDBX/mcp-github-memory-server)). An origin is one ParleyInn process lineage on one machine, sandbox or worktree. Each keeps its own gap-free sequence, which matches the per-project `seq` the SRS already mandates. Seal events into immutable, content-addressed segments and write them in the C2SP tlog-tiles layout: files that never change once written, plus one small signed checkpoint ([C2SP](https://c2sp.org/tlog-tiles)). This adds Merkle inclusion and consistency proofs to the linear chain. Any dumb carrier can move it without merging: a git ref, a bucket, rsync or a zip. Anthropic's own Access Transparency log already uses this format and advises keeping the last checkpoint, because "that saved checkpoint is what turns 'the log is consistent today' into 'the log has been consistent since you started watching'" ([Claude Platform docs](https://platform.claude.com/docs/en/manage-claude/access-transparency-log)). A network-free subset needs about three Go modules; torchwood's root package should not be imported ([torchwood](https://pkg.go.dev/filippo.io/torchwood); [sumdb/tlog](https://pkg.go.dev/golang.org/x/mod/sumdb/tlog)). That cost counts against the ten-dependency target and needs an ADR. The alternative is a small in-tree implementation.

Chain hashes of payloads, not payloads. immudb commits to H(metadata, key, SHA-256(value)) so retention can delete value bytes while every proof still verifies ([immudb](https://github.com/codenotary/immudb)). Hypercore hashes ciphertext, so a mirror without the key can still verify and serve blocks ([Hypercore](https://github.com/holepunchto/hypercore)). ParleyInn's REC-09 payload store and purge semantics already point this way. Extending it to per-session data keys makes shared segments safe to publish as ciphertext and erasable by deleting the key. Happy shows the useful variant for sandboxes: per-session keys wrapped to an account public key, so a sandbox can append history but cannot read anyone else's ([Happy](https://github.com/slopus/happy)). Happy also shows that confidentiality is not integrity, because its ciphertexts carry no associated data and no chain.

### What to decide now, inside v1's scope

NG4 keeps shared stores out of v1, and nothing above needs to ship before OQ-07 is resolved. Four v1 decisions are cheap now and expensive later, though. First, record an origin identity in the chain's genesis and canonical field set, so per-origin chains need no migration. Second, pin the RFC 8785 field set and encoding version in `meta`, and test that the Go encoder does not HTML-escape. Third, keep the chain committing to payload hashes, so purge and future key-shredding never break verification. Fourth, keep compaction an event, with limits applied only on the read path. Cloudflare's line is "Sessions stays lossless; context shapes" ([Cloudflare Agents](https://developers.cloudflare.com/agents/api-reference/agents-api/)), and OpenHands records compaction as a Condensation event ([OpenHands](https://docs.openhands.dev/sdk/guides/convo-persistence.md)). ParleyInn's own code should stay on git and GitHub. Individual contributors can use jj on top if they like, since it stays git-compatible.

Several points remain open, and a short spike would settle the first three. No benchmark exists of git under sustained machine-rate commits to one repository. GitHub does not say what happens past 6 pushes a minute, or how rulesets and push protection treat `refs/parinn/*` ([GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)). Claude Code's web sandbox proxy checks that a push goes only "to the configured branch" ([Anthropic](https://anthropic.com/engineering/claude-code-sandboxing)), and users report only `claude/*` branches pass ([issue mirror](https://claudeissues.com/issue/24535-allow-pushing-to-the-task-assigned-branch-not-just-claude-branches)). Sandboxes may therefore need the relay rather than git. Riding on the session branch would mix the record into the pull request and breach I8. The spike should push 10,000 segment commits under `refs/parinn/*` to private GitHub and default Forgejo, with and without reftable, and through the sandbox proxy. Other gaps cannot be closed by a spike. No regulator-grade source says crypto-shredding satisfies GDPR erasure. No documented incident of prompt injection through a committed transcript was found; the risk is argued by analogy to repository-file and memory poisoning ([Unit 42](https://unit42.paloaltonetworks.com/?p=160017)). Delta's licence and self-hosting model are unpublished. Vendor throughput figures from Cursor, Oak, Diversion and GitLab are self-reported.

## Conclusion

The agent era is not ending git. It is splitting version control into three layers that used to be one. Code snapshots stay in git because every host, CI system and model speaks it. Forge storage is being rebuilt as write-ahead logs on object storage behind git's protocol. The record of how code came to be written is a new artifact, and no one is putting it in git. Cursor's Continuity and ParleyInn's I10 make the same bet: the append-only log is the truth, and repositories, indexes and views are caches you can throw away and rebuild. The question "git or something else?" is therefore the wrong axis. The right one is which component holds authority. For ParleyInn the answer is the hash-chained record, and git becomes one of several couriers.

The evidence also changes what "security-first" has to mean once records travel. Every documented leak came from a convenience default: Entire's silent fallback, memento's wildcard refspec, claude-context-sync's plaintext fallback. Every documented loss came from a shared mutable lane. Every injection path came from stored text that was trusted on recall. ParleyInn's invariants already forbid all three. The work left is to make the sharing layer obey them too: one writer per lane, signatures that bind history rather than snapshots, ciphertext on every shared carrier, and foreign records that reach the model only when asked and only inside an envelope. Real-time sharing is a separate product, the relay, and should be built and reviewed as one.
