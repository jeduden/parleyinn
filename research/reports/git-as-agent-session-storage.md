# Let git carry ParleyInn's record, not serve it

ParleyInn should not make git the place where all agent session history *lives*. It should make git the place where sealed, signed, append-only segments of that history are *published*: written under per-origin custom refs in batches, and pushed by the user's own git, never by ParleyInn. The evidence on this is consistent. Every multi-writer system that has run at scale keeps git out of its hot path. Beads dropped its git-tracked JSONL source of truth for a Dolt database after what its author called "two sources of truth, race conditions, and tombstone hell". Gas Town runs live state on one SQL server and sends only a 15-minute append-only ledger to git. Forgejo and Gitea, both Go forges, keep issues and comments in SQL. Block's Buzz keeps signed events in Postgres. Git can hold millions of messages only if they are batched into segment files of about a megabyte, and even then a busy record heads toward the tens of gigabytes that GitHub's 10 GB guidance treats as outside a healthy repository. Git has no query index, so recall needs the local SQLite FTS5 index the proposal already plans. Git does solve durable, reviewable, asynchronous sharing across machines, sandboxes and open-source publication. It does not solve real-time sharing: GitHub recommends at most 6 pushes per minute per repository, and its webhooks are not retried. It does not solve secret erasure either. The working proposal survives the evidence, provided ParleyInn adopts about a dozen concrete design rules taken from Radicle, git-bug, Fossil, Entire and Beads, and provided the real-time relay stays out of the core binary.

## Every multi-writer system that lasted pulled git out of the hot path

The clearest story is Beads, Steve Yegge's agent-memory tracker. From October 2025 to February 2026 it kept a gitignored SQLite cache plus a **git-tracked `.beads/issues.jsonl` that was the source of truth**. A 5-second debounced export and an import after `git pull` kept the two in step, and a custom field-level merge driver plus 30-day tombstones resolved conflicts ([v0.47.0 ARCHITECTURE.md](https://github.com/steveyegge/beads/blob/v0.47.0/docs/ARCHITECTURE.md), [DELETIONS.md](https://github.com/steveyegge/beads/blob/v0.47.0/docs/DELETIONS.md)). Releases v0.50 and v0.51 removed the daemon (~19,700 lines), the JSONL sync layer (~7,600 lines), the 3-way merge engine and the tombstone system, and made `bd sync` a no-op. **Dolt became the sole store** at v1.0.0 in April 2026 ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)). Yegge summed up the old design as "bidirectional sync, 3-way merge, two sources of truth, race conditions, and tombstone hell", with a "22-nose Clown Show" of data-loss incidents ([Yegge, mirror](https://drss.io/feed/npub1na2ppcvpx7m7dg4d2rqelpq4xdj9z40cxu3avh4qcdq8dtupdcmqahmfge/gas-town-from-clown-show-to-v10)). Today Beads still uses the git remote, but only as a wire: Dolt history rides under **`refs/dolt/data`**, apart from code branches, so branch protection and code history are untouched ([sync-concepts.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)). The Dolt era brought its own failures. One commit per write grew to "gigabytes of storage for a few thousand beads", and the only fix rewrites history so that "every other clone … must re-clone" ([history-squash.md](https://github.com/gastownhall/beads/blob/main/docs/recovery/history-squash.md)). A 2026-08-11 accidental release took part in a fleet-wide data-loss incident ([CHANGELOG](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md)).

ParleyInn should draw a precise lesson from Beads. The failures came from **mutable rows reconciled across replicas**: resurrected deletes, split-brain and re-initialising over missing data. They did not come from git as such. ParleyInn's record is append-only, so deletes and field merges never arise. The two-stores trap remains whenever a local store and a git copy can each be edited and then reconciled.

Gas Town, built on Beads, shows the architecture that results. All agents in a town write to **one Dolt SQL server on `main` in transactions** for immediate visibility. Git holds code worktrees, plus a "Ledger" plane in which a "JSONL Dog" exports scrubbed, append-only snapshots to GitHub every 15 minutes ([dolt-storage.md](https://github.com/gastownhall/gastown/blob/main/docs/design/dolt-storage.md), [ledger-export-triggers.md](https://github.com/gastownhall/gastown/blob/main/docs/design/ledger-export-triggers.md)). Real-time signalling is tmux `gt nudge`. Persistent mail costs a Dolt commit per message: "4 agents x 15 patrol cycles x 2 mails per cycle = 120 commits just for routine chatter" that "live in the git history forever" ([mail-protocol.md](https://github.com/gastownhall/gastown/blob/main/docs/design/mail-protocol.md)). Gas Town also has exactly the gap ParleyInn targets. It stores no session record of its own. It scrapes Claude Code's `~/.claude/projects/*.jsonl`, and its own audit concedes that "no single ID connects" transcript, cost, event and bead, and that 17 of 28 touch points depend on Claude Code internals ([agent-api-inventory.md](https://github.com/gastownhall/gastown/blob/main/docs/design/agent-api-inventory.md)).

The other systems repeat the split. Forgejo and Gitea store code as bare git repositories but keep issues, comments and PRs in SQLite, MySQL or Postgres, and notify through HMAC-signed webhooks ([Forgejo config](https://forgejo.org/docs/latest/admin/config-cheat-sheet/), [Gitea webhooks](https://docs.gitea.com/usage/webhooks)). Buzz, which Block announced in July 2026, is "a Nostr relay" in which every message, workflow step and git event is a signed event in one log. That log lives in **Postgres with FTS**, with Redis for pub/sub and git served by the relay over NIP-34 and smart HTTP ([block/buzz](https://github.com/block/buzz)). Fossil puts immutable hash-named artifacts in one SQLite file, rebuilds ticket tables from them, and deliberately keeps chat out of sync: chat is local, long-polled and deleted after 7 days ([Fossil chat](https://fossil-scm.org/home/doc/trunk/www/chat.md), [tickets](https://fossil-scm.org/home/doc/trunk/www/tickets.wiki)). Even git-bug, the purest git-native design, answers queries from a rebuildable excerpt cache and a bleve index under `.git/git-bug/`, not from git ([cache/subcache.go](https://github.com/git-bug/git-bug/blob/master/cache/subcache.go)).

The full-transcript tools tell a consistent story. Only Entire and claude-git-sessions put **full verbatim transcripts into git by default**, and both keep them off the code branch. The attribution tools went the other way: git-ai and Agent Trace keep transcripts out of git, and git-ai once embedded messages, then removed them. No surveyed tool combines verbatim transcripts, many writers, a tamper-evident append-only record, and treating recalled content as untrusted. That combination is the niche ParleyInn would occupy.

## Millions of messages fit in git only as sealed, batched segments

Git can hold millions of messages if they are not millions of objects. GitHub enforces two hard caps, **100 MB per object** and **2 GB per push**, and recommends a 1 MB object maximum. Everything else is guidance: **10 GB on disk**, ideally under 1 GB and "strongly" under 5 GB; 5,000 branches; 3,000 entries per directory; 15 git reads per second; and **6 pushes per minute per repository** ([GitHub repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits), [large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)). GitHub does intervene when repositories load its backend. Nixpkgs reached about 83 GiB with half a million trees, and GitHub reported failing maintenance jobs and named "changes to Git refs, the total number of refs and trees" as bottlenecks ([NixOS Discourse](https://discourse.nixos.org/t/nixpkgs-core-team-update-2025-11-30-github-scaling-issues/72709)). Cargo, Homebrew, CocoaPods, vcpkg and Go all hit walls using git as a database and moved lookup to HTTP or indexed layers. Homebrew cut auto-update from every 5 minutes to every 24 hours because GitHub "would rather we didn't" fetch that often ([Nesbitt](https://nesbitt.io/2025/12/24/package-managers-keep-using-git-as-a-database.html)).

A rough estimate gives the scale. Assume 2 KB per event on average; agent turns with tool output run much larger. Then 5 million events are about 10 GB before zlib compression and deltas. One busy team record therefore sits at or past GitHub's guidance within months. Holding that safely in git takes three rules. First, pack events into **sealed segments of about 1 MB**, one blob each, never one blob per event. Second, shard paths and refs so no directory or ref list nears the recommended caps; Entire's two-character ref shards are a working model ([entireio/cli](https://github.com/entireio/cli)). Third, spread large records across repositories by project or tenant, which also matches I8. Self-hosted Forgejo removes GitHub's guidance but has its own defaults: a **60 s gc timeout and 300 s clone and pull timeouts**, which a tens-of-GB repository will exceed unless the operator raises them ([Forgejo config](https://forgejo.org/docs/latest/admin/config-cheat-sheet/)). Windows' 300 GB repository needed a custom virtual file system and cache servers before clones finished in minutes ([Brian Harry](https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/)).

Fast retrieval rules git out as the query layer. Git has no content index. Pickaxe and `git grep` over revisions walk history and need the blobs present. Blobless clones fetch blobs on demand, which makes history walks slow, and GitHub advises against shallow clones except for throwaway builds ([GitHub Blog](https://github.blog/open-source/git/get-up-to-speed-with-partial-clone-and-shallow-clone/)). vcpkg found that git cannot even answer which commit added a given tree, because it keeps no reverse index ([Nesbitt](https://nesbitt.io/2025/12/24/package-managers-keep-using-git-as-a-database.html)). The working precedent for the proposal's SQLite FTS5 index is git-bug. It records, per entity, the commit that its excerpt and index were "builtFrom", treats any mismatch as an error, and wipes and re-indexes in batches. Its benchmark comment shows a 26 MB bug index rebuilt in about 1.3 to 1.5 s for its test set ([subcache.go](https://github.com/git-bug/git-bug/blob/master/cache/subcache.go)). Before that cache existed, listing 1,000 bugs took 25 to 29 s and reading 10,000 took about 40 s ([git-bug issue](https://git.secluded.site/git-bug/bug/f8e9e6cfda83ab8dc958d4211d6c699d8ab61594aa6beac0c1012f72526cd65c)). That gap is the difference between querying git and querying an index.

Ref count is the remaining scaling risk. One ref per session per origin becomes tens of thousands of refs, past GitHub's 5,000-branch guidance and into the ref churn that hurt Nixpkgs. Reftable, the Git 3.0 default for new repositories, makes many refs much cheaper locally: fetch is 22x faster and push 18x faster at 10,000 refs ([GitLab on Git 2.51](https://about.gitlab.com/blog/what-s-new-in-git-2-51-0/)). Hosts still count each ref. **One ref per origin**, with each new segment as a new commit, keeps the count at the number of nodes and sessions that are actually live.

## Git solves durable sharing, not live sharing

The question names seven sharing scenarios. Git's fit differs sharply between them.

| Need                          | Does git solve it?                            | Why, and on what condition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Multi-agent** (one machine) | Partly; the local store matters more          | Per-writer refs never contend, as Radicle's namespaces and claude-git-sessions' UUID files show ([Radicle](https://radicle.dev/guides/protocol), [ccgs](https://github.com/ingram-technologies/claude-git-sessions)). Local concurrency is a file-locking problem; jj's lock-free head files are an option ([jj](https://docs.jj-vcs.dev/latest/technical/concurrency/)).                                                                                                                                                                                                                          |
| **Multi-worktree**            | Yes, if the record is not in the working tree | Beads now shares one store across all worktrees and dropped worktree-committed sync after its daemon committed to the wrong branch ([worktrees.md](https://github.com/gastownhall/beads/blob/main/docs/reference/worktrees.md), [v0.47.0](https://github.com/steveyegge/beads/blob/v0.47.0/docs/GIT_INTEGRATION.md)). | **Multi-machine**             | Yes, asynchronously                           | `refs/<ns>/*` fetch and push refspecs plus union work for git-bug and Beads ([gogit.go](https://github.com/git-bug/git-bug/blob/master/repository/gogit.go)). | **Cloud sandbox**             | Often, but unproven for custom refs           | Claude Code on the web pushes through a proxy that checks "it is only pushing to the configured branch" ([Anthropic](https://anthropic.com/engineering/claude-code-sandboxing)); users report only `claude/*` branches are allowed ([#24535](https://claudeissues.com/issue/24535-allow-pushing-to-the-task-assigned-branch-not-just-claude-branches)). | **Open source**               | Yes for publishing; poorly for erasure        | Push protection is on by default for public pushes and will block transcripts that contain recognised secrets ([push protection](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)). Removal is a Support ticket, and data persists in forks and clones ([removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). About 2.4% of public AI-config directories hold verified secrets ([ironpeak](https://ironpeak.be/blog/leaking-secrets-from-the-claud/)). |
| **Forgejo instead of GitHub** | Same model, fewer caps                        | It removes GitHub's push and size guidance, but Forgejo keeps its own collaboration data in SQL, not git. Treat it as a remote, not a component to embed.                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Real-time**                 | No                                            | 6 pushes per minute per repository; webhooks must answer within 10 s, failures are not redelivered, and receiving them needs a public endpoint ([webhook failures](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)). Radicle needs a gossip daemon and Fossil's chat needs a server. With 20 agents on one repository, each could push about every 3 to 4 minutes.                                                                                                                                                                                          |

Real-time is where the proposal's separate relay earns its place. Buzz shows what a relay costs: Postgres, Redis and object storage ([block/buzz](https://github.com/block/buzz)). Fossil shows the discipline: live chat stays out of the durable record ([Fossil chat](https://fossil-scm.org/home/doc/trunk/www/chat.md)). For ParleyInn, the relay should carry the **same signed segments, or announcements of their hashes**, so the record stays the one source. The relay then buys latency, git buys durability, and neither creates a second truth. I4 already forces this layout: git push, fetch, webhooks and relays are all network, so all of them sit outside the shipped binary.

## The proposal holds if ParleyInn adopts twelve design rules

The working proposal has five parts: per-origin, content-addressed, hash-chained segments; git as a transport the user pushes; a local FTS5 index rebuilt from segments; a relay outside the core; and no network in ParleyInn itself. The evidence supports that design, and its pieces have precedents: git-bug for commit-per-pack and the builtFrom check, Radicle for per-writer namespaces, Fossil for union and derived tables, and Beads and Entire for custom refs on the user's remote. The risks lie in the details, so the rules below are the substance of the recommendation.

| #   | Rule                                                                                                                                                                                                                                                                                                                       | Precedent                                                                                                                                                      | Invariant |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 1   | **The local segment store is the record; git is a one-way, deterministic encoding of the same bytes.** Imports are union-by-hash of verified segments. | 2   | **One ref per origin, e.g. `refs/parinn/<tenant>/<node>/<session>` or one per node, sharded; never one per event or per message.** Keep live refs well under 5,000 per repository.                                                                                                                                         | Entire shards ([cli](https://github.com/entireio/cli)); Radicle namespaces; Nixpkgs ref load                                                                   | I1, I8    |
| 3   | **Seal segments by size (~1 MB) or by session end, and make one commit per segment.** Never commit per event.                                                                                                                                                                                                              | Dolt history bloat ([history-squash](https://github.com/gastownhall/beads/blob/main/docs/recovery/history-squash.md)); Gas Town mail commits                   | I9        |
| 4   | **Budget pushes per repository, not per agent: at most one push per session end or per few minutes, staying inside about 6 pushes per minute across all writers.**                                                                                                                                                         | [GitHub limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)                                                  | I9        |
| 5   | **Each segment's signature covers its own hash and its predecessor's hash**, so an old (segment, signature) pair cannot be replayed as a new head.                                                                                                                                                                         | Radicle sigrefs replay, fixed with a parent binding in 1.7.0 ([disclosure](https://radicle.dev/2026/03/30/disclosure-of-vulnerability-in-signed-references))   | I1        |
| 6   | **Detect equivocation and truncation:** two successors of one predecessor from the same origin, or a head that moves backwards, is audited and counted, and never silently resolved. Three judgement calls go beyond the evidence. The first is whether to write segments as git objects in a ParleyInn-owned bare repository (git-bug's model) or as plain files mirrored into git on export. Rule 1 permits either, as long as the bytes and hashes are identical and the flow is one-way. The fast-import route avoids adding a dependency against the ten-dependency target, and avoids any ADR question about go-git's network-capable packages. The second is the cloud sandbox. Until it is shown that sandbox proxies accept `refs/parinn/*`, sandbox persistence should fall back to an explicit, user-configured route rather than quietly riding on the session's code branch; quiet piggybacking would breach both I6 and I8. The third is erasure. Append-only, content-addressed history cannot honour a deletion request once it is pushed. Encrypting segments with per-tenant or per-session keys, and deleting the key to erase (crypto-shredding), is the only design that keeps I1 for the record while allowing practical erasure. No regulator-grade source in the notes confirms that this satisfies GDPR.

## Eight questions the evidence leaves open

Several load-bearing numbers are missing. No benchmark of git at tens of millions of small objects was found, covering repack, commit-graph or multi-pack-index costs. Nor was any per-push latency figure. GitHub does not say what happens when a repository exceeds 6 pushes per minute, whether throttling or a support contact. No source covers how GitHub branch protection, rulesets or push protection treat non-`refs/heads` namespaces such as `refs/parinn/*`, or whether the Claude Code sandbox proxy accepts them; the `claude/*` restriction comes from community issue mirrors. Nobody has published repository growth per session or per month for Entire, SpecStory or claude-git-sessions, or the size of Beads' `refs/dolt/data`. Radicle and Fossil publish no scale numbers. git-bug has no current benchmark at 10,000 to 100,000 entities with its bleve cache. Whether Buzz stores full agent transcripts or only messages agents post was not verified, and the identification of "Buzz" as Block's project needs stakeholder confirmation. No documented real incident of prompt injection specifically through a committed agent transcript was found; the risk is argued by analogy to repository-file and memory poisoning. Finally, the GDPR status of crypto-shredding rests on vendor and blog opinion only. A short spike would settle the first three: push 10,000 segment commits under `refs/parinn/*` to a private GitHub repository and a default Forgejo instance, with and without reftable, and through the sandbox proxy.

## Conclusion

The question "should ParleyInn store everything in git?" conflates two roles that every successful system keeps apart: the store an agent queries in milliseconds, and the log that crosses machines and survives them. ParleyInn's append-only, single-writer-per-origin record is unusually well suited to the second role. It removes the field merges and resurrected deletes that sank Beads' git era, and it turns sync into a set union, so git can be a transport that is genuinely safe in a way it was not for mutable trackers. That suitability holds only if git never becomes a second truth, never sets the pace of appends, and is never the path by which another origin's text reaches the model.

The evidence also exposes a new design obligation. Once segments travel, the threat model gains rollback, equivocation and replay by other origins, and Radicle's 2026 flaw shows that a signed snapshot is not a signed history. ParleyInn's hash chain gives it the right primitive. The work left is to sign the chain head with its predecessor bound in, to count every fork it sees, and to treat every fetched byte as enveloped, pull-only data. Real-time sharing is a separate product, the opt-in relay, and should be built and reviewed as one.
